# Integration: how fca-frontend consumes this API

**This file is authoritative.** `fca-frontend/docs/integration.md` mirrors it from the consumer side. If they disagree, this one wins; fix the other.

## At a glance
| Item | Value |
|---|---|
| API base URL (local) | `http://localhost:3001/api/v1` |
| Swagger UI / raw document | `http://localhost:3001/api/docs` · `/api/docs-json` |
| Web app origin (local) | `http://localhost:5173` (allowed by `CORS_ORIGINS`) |
| **Contract version** | **0.12.0** (`src/meta/contract-version.ts`, `contracts/openapi.json` `info.version`, `GET /meta`) |
| API major | `v1` (URL prefix) |
| Content type | `application/json`; errors `application/problem+json` |
| Tenant routes | `/api/v1/organisations/:organisationId/…` |
| Non-tenant routes | `/auth/*`, `/me`, `/frameworks`, `/plans`, `/platform/*`, `/health*`, `/meta` |

Local ports: API **3001**, web **5173** (Vite dev), 4173 (Vite preview). Neon is remote; there is no local Postgres or mail server.

## Contract workflow
1. Backend change → `npm run openapi:export` → bump `CONTRACT_VERSION` → add `contracts/CHANGELOG.md` entry → `npm run verify`.
2. Frontend: `npm run api:sync` (copies `../fca-backend/contracts/openapi.json` to `contract/openapi.json` and writes `contract/CONTRACT_VERSION`; override the path with `FCA_BACKEND_PATH`) → `npm run api:codegen` → `npm run verify`.
3. Semver: additive = minor, breaking = major, docs-only = patch. While `0.x`, the frontend treats a different **minor** as incompatible. At runtime the frontend compares `GET /meta` → `contractVersion` with its pin and shows a mismatch warning.
4. Never import across repositories. The only artefact that moves is the OpenAPI document.

## Authentication (from Phase 2b; see ADR-0003)
- `Authorization: Bearer <access token>` (≈15 min, kept in memory by the SPA).
- Refresh: `POST /api/v1/auth/refresh` with the `HttpOnly` cookie (send `credentials: 'include'`); on boot and after a 401 (single-flight). Cookie is `SameSite=Lax`, scoped to `/api/v1/auth`.
- Production requires web and API to be **same-site** (shared registrable domain) or a host rewrite of `/api/*`. Two Vercel projects — `fca-web.vercel.app` and `fca-api.vercel.app` — share the registrable domain `vercel.app`, so they are same-site and the refresh cookie travels; two different registrable domains are not, and the session then cannot refresh. `CORS_ORIGINS` must name the deployed web origin exactly. See [deployment-vercel.md](deployment-vercel.md).
- Cookie endpoints (`/auth/refresh`, `/auth/logout`) also require the header `X-Requested-With: fca-web` (CSRF defence; allowed by CORS) in addition to the exact-origin check.
- Verification, reset and invitation links open **SPA pages** that POST the token; the API never consumes tokens on GET.

### Contract for the web app (built in Phase 2b, contract 0.2.0)
| Call | Success | Failure codes the UI must handle |
|---|---|---|
| `POST /auth/register` `{ email, password, fullName }` | `202 { accepted: true }` (always, even for an existing address: say "check your email") | `400 VALIDATION_FAILED` with `errors[]` paths `email`, `password`, `fullName`; password codes `password.tooShort`, `password.tooLong`, `password.tooCommon`, `password.tooSimple`, `password.containsEmail` |
| `POST /auth/resend-verification` `{ email }` | `202` (always) | |
| `POST /auth/verify-email` `{ token }` | `204` | `400 INVALID_TOKEN` (used, expired or unknown: offer "resend") |
| `POST /auth/login` `{ email, password }` | `200 { accessToken, tokenType: "Bearer", expiresInSeconds }` + `fca_refresh` cookie | `401 INVALID_CREDENTIALS`, `403 EMAIL_NOT_VERIFIED` (offer resend), `429 RATE_LIMITED` with `Retry-After` (seconds), `503 DATABASE_UNAVAILABLE` with `Retry-After` |
| `POST /auth/refresh` (cookie + `X-Requested-With: fca-web`, no body) | `200` (same body as login), cookie rotated | `401 UNAUTHENTICATED` (cookie cleared: go to sign-in), `403 FORBIDDEN` (header missing: a client bug) |
| `POST /auth/logout` (cookie + header) | `204`, cookie cleared | |
| `POST /auth/forgot-password` `{ email }` | `202` (always) | |
| `POST /auth/reset-password` `{ token, password }` | `204`; every session of the user is ended: sign in again | `400 INVALID_TOKEN`, `400 VALIDATION_FAILED` (weak password; the link is **not** consumed) |
| `GET /me` (bearer) | `200 { id, email, fullName, emailVerified, createdAt }` | `401 UNAUTHENTICATED` |

- **Cookie**: name `fca_refresh`, `HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth`, `Secure` in production. JavaScript never sees it; fetch with `credentials: 'include'`.
- **Access token**: send as `Authorization: Bearer`; keep in memory only. After any `401` on an API call, call `POST /auth/refresh` once (single-flight) and retry; a failed refresh means signed out. Two tabs refreshing at the same moment is tolerated (10-second grace); a token replayed after that signs the session out everywhere.
- **Email links** open SPA routes and carry the one-time token in the URL **fragment**: `/verify-email#token=…`, `/reset-password#token=…` (read `location.hash`, POST the token, then clear the fragment from the address bar). Emails also link to `/login` and `/forgot-password`.
- Everything except `/health*`, `/meta` and `/auth/*` requires the bearer token.
- `503 DATABASE_UNAVAILABLE` (with `Retry-After: 5`) means the database is unreachable or waking up: show a "try again" state, not a generic error.
- **Dev mail**: with `MAIL_TRANSPORT=file` no email is delivered; messages are written to `DEV_MAIL_DIR` (default `.dev-mail`, git-ignored) as `.eml` files and the link is logged by the API. A real provider is a gate G0 decision.
- **Operational endpoint (not in the contract)**: `POST /api/v1/internal/jobs/tick` is called by a host scheduler, signed with `X-FCA-Timestamp` (unix seconds) and `X-FCA-Signature` = hex HMAC-SHA256 of `"<timestamp>.POST./api/v1/internal/jobs/tick"` with `JOBS_TICK_SECRET`; answers `200 { claimed, succeeded, retried, dead }`, `401` on a bad signature, `404` when no secret is configured.

## Conventions
- **Errors** (RFC 9457): `{ type, title, status, detail?, code, errors?: [{ path, code, message? }], requestId }`. Branch on `code`. `requestId` equals the `X-Request-Id` response header; show it in "report a problem" UI.
- **Request id**: send `X-Request-Id` (8–64 chars `[A-Za-z0-9._-]`) to correlate; otherwise one is generated.
- **Pagination** (cursor, no offset): `?limit=` (1 to 100, default 50) and `?after=<nextCursor>`; response `{ items, nextCursor }` (`nextCursor` is null on the last page).
- **Idempotency**: creating `POST`s accept `Idempotency-Key`.
- **Concurrency**: updates carry the resource `version`; a stale one → `409 VERSION_CONFLICT`.
- **Dates**: instants are ISO 8601 UTC; date-only fields are `YYYY-MM-DD`; deadlines are evaluated in the organisation's timezone on the server.
- **Metric states** (dashboard): `availability` (`ok|not_configured|not_assessed|no_records|unable_to_calculate`) + `status` (`in_progress|compliant|needs_attention|overdue|null`, only meaningful when `availability` is `ok`); never infer them client-side. `compliant` is labelled **"Meets target"** — no surface calls an unassessed thing non-compliant. A measured figure is always the coverage triple `{ value, assessed, applicable }`, and `value: null` is "not assessed", never 0 (see "Executive dashboard" below).
- **Status codes**: 400 validation, 401 unauthenticated, 403 lacks permission (member), 404 unknown **or foreign** record, 409 conflict, 422 domain-rule violation, 429 rate limited, 503 dependency down.
- **CORS**: exact origins from `CORS_ORIGINS`, credentials allowed; allowed request headers `Content-Type`, `Authorization`, `X-Request-Id`, `X-Requested-With`, `Idempotency-Key`; exposed response headers `X-Request-Id`, `Content-Disposition` (needed to name downloads).

## Organisations and access (Phase 2c, contract 0.3.0)

Every operation in the contract carries `x-access` (`public` · `authenticated` · `permission` · `organisation-member` · `platform`) and, where it applies, `x-permission` (a key of the catalogue in [rbac-matrix.md](rbac-matrix.md)). The frontend reads what the CALLER may do from `GET /organisations/:organisationId/me` (`role` and `permissions`) and uses it to show or hide actions; the server enforces every permission on every request.

| Method | Path | operationId | Access | Notes |
|---|---|---|---|---|
| GET | `/organisations` | `listMyOrganisations` | authenticated | the caller's active organisations with their role |
| POST | `/organisations` | `createOrganisation` | authenticated | self-serve; `403 SELF_SERVE_DISABLED` unless `ORGANISATIONS_SELF_SERVE` is on (`GET /meta` → `organisationSelfServe`) |
| GET | `/organisations/{organisationId}/me` | `getMyMembership` | organisation-member | role + every permission of the role |
| GET | `…/members` | `listMembers` | `users.view` | cursor page |
| PATCH | `…/members/{membershipId}` | `changeMemberRole` | `users.edit` | body `{ role, version }` |
| POST | `…/members/{membershipId}/deactivate` · `/reactivate` | `deactivateMember` · `reactivateMember` | `users.delete` | body `{ version }` |
| GET · POST | `…/invitations` | `listInvitations` · `createInvitation` | `users.view` · `users.create` | `state` includes the computed `EXPIRED` |
| POST | `…/invitations/{invitationId}/resend` · `/revoke` | `resendInvitation` · `revokeInvitation` | `users.create` | resend: at most one email per 5 minutes |
| POST | `/invitations/inspect` · `/invitations/accept` | `inspectInvitation` · `acceptInvitation` | authenticated | body `{ token }` |
| GET · POST | `/platform/organisations` | `listPlatformOrganisations` · `provisionOrganisation` | platform | names and counts only; provisioning invites the first Owner |

- **404 versus 403.** A non-member, a deactivated member and an unknown organisation all get `404`; a member whose role lacks the permission gets `403`, decided before anything is looked up. The UI shows one "not found" for the three 404 cases.
- **Roles.** Only an Owner grants, changes or removes the Owner role (`403 OWNER_ONLY`); nobody changes their own role or deactivates themselves (`403 SELF_CHANGE_NOT_ALLOWED`); an organisation always keeps one active Owner, also under concurrent requests (`409 LAST_OWNER`).
- **Invitation link.** The email links to the SPA page `/accept-invitation#token=…` (token in the fragment, POSTed by the page). The invitee signs in (or registers and confirms) with the **invited address** and accepts. Wrong account: `403 INVITATION_EMAIL_MISMATCH`; unconfirmed address: `403 EMAIL_NOT_VERIFIED`; unknown, expired, used, revoked or replaced link: one uniform `400 INVALID_TOKEN`.
- **Platform administrators** are made with `npm run platform-admin -- grant <email>` (owner credentials, direct database URL), never through the API. They see names and counts only and are not members of what they provision.

## Setup modules (Phase 3, contract 0.4.0)

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.4.0) and in the contract itself (`x-access` / `x-permission`). What the generated types do not say:

- **PATCH semantics** (settings, regulator contacts, business units): a field left out keeps its value; `null` or a blank string clears it; `version` is required and a stale one is `409 VERSION_CONFLICT`. Required fields are the exception: `name`, `timezone`, **`country` and `dpoEmail` cannot be cleared**; sending `null` or a blank string for them leaves the value unchanged (no error), so the form must validate them itself. `GET …/settings` returns `country` and `dpoEmail` as `null` for an organisation created before they were asked for (every organisation provisioned or created through the API until now), which the UI should show as "incomplete".
- **Display name** needs `company.branding` on top of `company.edit` (`403` otherwise); the form should disable that one field for roles without it.
- **Logo**: `PUT …/settings/logo` is `multipart/form-data` with the single field `file` (PNG or JPEG, up to 512 KiB; `413` too large, `415` not an accepted image, decided by the bytes, never by the file name). `GET …/settings/logo` answers the image with `ETag` (honour `If-None-Match`), `Cache-Control: private`, `nosniff`; it needs the bearer token, so fetch it with the API client and show a blob URL, not a bare `<img src>`. `404` = no logo. Changing the logo does **not** change the settings `version`; the settings fields `hasLogo` and `logoUpdatedAt` tell whether there is one and when to refetch.
- **Business unit fields**: `headMembershipId` must be an ACTIVE member (field error `headMembershipId` / `notAnActiveMember`); `sensitivity` is 1 (Public) to 5 (Critical) or `null` = not classified (the labels are a frontend display concern); `employeeCount` ≥ 0 or `null`; `parentId` must be an active unit, not itself and not a descendant (field errors `parentId` / `unknownParent`, `parentArchived`, `parentIsSelf`, `parentCycle`). The DTO also returns `headName` and `parentName` so a table needs no extra calls. `code` is unique per organisation **including archived units**; `name` is unique among active units.
- **Archive**: `POST …/archive` is refused with `409 BUSINESS_UNIT_HAS_CHILDREN` while active children exist (the `detail` is plain language: show it). Archived units are listed only with `?includeArchived=true`.
- **Frameworks**: `GET /frameworks` is the catalogue (identifiers only: `code`, `name`, `jurisdiction`, `kind`; never legal text). `GET …/frameworks` returns the same entries with `applicable`, `addedAt` and `removedAt`. `PUT …/frameworks` sends the **complete desired set** `{ frameworkIds }`; an id that is not in the catalogue is `400 VALIDATION_FAILED` (`frameworkIds` / `unknownFramework`). The response is the resulting list.
- **Plans and limits**: `GET /plans` lists the visible plans. `GET …/subscription` returns `{ assigned, planCode, planName, maxUsers, apiAccess, assignedAt, activeMembers, pendingInvitations }`; `assigned: false` means **no plan and nothing is limited** (never show "0 users allowed"); `maxUsers: null` with a plan means unlimited. Plans carry `isPlaceholder`. When a limit is reached, inviting and reactivating answer `403 USER_LIMIT_REACHED`; the count is active members plus open invitations. The seeded plans and their limits are **placeholders**.
- **Platform**: `GET /platform/plans` includes hidden plans; hiding a plan never changes an organisation that already has it; `PUT /platform/organisations/{id}/plan` copies the plan's limits into a snapshot for that organisation; `POST /platform/organisations` accepts an optional `planId`.

## Compliance mapping (Phase 4, contract 0.5.0)

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.5.0) and in the contract (`x-access` / `x-permission`). What the generated types do not say:

- **Framework content is not seeded.** A fresh installation has no versions and no requirements: `GET /frameworks/reference-guide` returns every catalogue framework with `currentVersion: null`, which the UI shows as "No verified content yet". Content arrives only when the platform owner verifies and loads a pack (`npm run frameworks:verify`, `npm run frameworks:load`; see [neon-setup.md](neon-setup.md) section 8). Never hard-code a framework list or requirement text in a client.
- **Requirements** (`GET /framework-versions/{versionId}/requirements`) are identifiers and headings (`ref`, `kind`, `title`, `description`) in the pack's order, with `textSource` saying whether the words are the source's own. A version has at most a few hundred; a picker may read every page (`limit=100`, follow `nextCursor`) and search in the browser. The id of the version to use is `currentVersion.id` of the reference guide.
- **The mapping table** is `GET …/compliance-mappings/matrix`: one row per governance area, plus on the FIRST page a row with `areaId: null` for mappings filed under no area. Each row has flat `entries`; every mapping contributes two entries (one per side), and the client places each in the column of its `frameworkCode`. The columns themselves come from `GET /frameworks`, not from the matrix. A relationship or review-status filter leaves out areas without a matching mapping. An archived area appears (`areaArchived: true`) only while it still holds mappings that pass the filters.
- **Creating a mapping** needs `fromRequirementId` and `toRequirementId` (two requirements of DIFFERENT frameworks, both in a verified version), `relationship`, a non-blank `rationale` and optionally `areaId`, `reference` and `reviewStatus` (default `DRAFT`). Field errors (`errors[].path` + code): `fromRequirementId` / `toRequirementId` with `unknownRequirement`, `requirementUnavailable`, `sameRequirement`; `toRequirementId` with `sameFramework`; `areaId` with `unknownArea`, `areaArchived`. The same pair twice (either direction) is `409 MAPPING_ALREADY_EXISTS`.
- **Editing**: `origin: SEED` mappings (copied from a verified pack) accept only `areaId` and `reviewStatus`; anything else is `400` with `seededMappingLocked`. `null` clears `areaId` and `reference`; `rationale` can be replaced but not cleared.
- **Load Default Mappings** (`POST …/compliance-mappings/load-defaults`, no body): `200 { inserted, skipped, failed[], frameworks[] }` or `422` with `SEED_DATA_UNAVAILABLE` / `NO_FRAMEWORKS_SELECTED` and nothing written; the `detail` is plain language: show it. Today no pack carries mapping entries, so the answer is `422 SEED_DATA_UNAVAILABLE` for every organisation until a cited crosswalk is loaded.
- Every surface that shows mappings carries `disclaimer` from the matrix or the reference guide: *informative, not legal equivalence, not legal advice*.

## Assessment, priorities, remediation, evidence and reports (Phase 5, contract 0.6.0)

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.6.0) and in the contract (`x-access` / `x-permission`). What the generated types do not say:

- **One policy, one truth.** `GET …/scoring` is the whole methodology as it applies to the organisation: exposure bands (`exposure_v1`, score = sensitivity × severity × likelihood, 1–125), the 1–5 sensitivity/severity/likelihood scales, the maturity levels, remediation due days, the Plan window and the Eisenhower questions. Every response also carries the reference defaults (`defaultBands`, `defaultRemediationDueDays`, `defaultPlanWindowDays`) and `customised*` flags, so the form can show "restore default". `PATCH` sends `version` — **0 when nothing has been customised yet** — and any of `exposureThresholds`, `remediationDueDays`, `planWindowDays`; `null` restores that one block. Thresholds must leave three non-empty bands under the top score, else `400` with `exposureThresholds` / `invalidThreshold`.
- **Never draw a band you were not given.** `attainableValues` lists the scores the product can actually produce; with the reference thresholds `CRITICAL` (≥ 91) is reached by only a few combinations. Show the band table as returned, not as a hard-coded legend.
- **Assessment lifecycle.** `DRAFT → IN_REVIEW → APPROVED`, plus `SUPERSEDED`. Only a DRAFT changes (`409 ASSESSMENT_NOT_EDITABLE` otherwise): items, template application, PATCH and DELETE are all refused on a submitted assessment. `submit` with no items is `422 ASSESSMENT_EMPTY`. `return` goes back to DRAFT and **requires** a `comment`; `approve`/`submit` take an optional one. `revise` answers 201 with a **new** DRAFT that revises this cycle and marks the old one SUPERSEDED in the same transaction; `POST …/assessments` can do the same from the start with `revisesAssessmentId` (which must be APPROVED or SUPERSEDED: field error `revisesAssessmentId` / `notApprovedForRevision`). `DELETE …/assessments/{id}` is a DRAFT-only delete with the `version` as a **query** parameter, not a body.
- **An assessment freezes its own bands.** `methodology` and `exposureBands` are stored when it is created, so an older assessment keeps the thresholds it was rated with even after the organisation changes them. Render a risk label from that snapshot, not from `GET …/scoring`.
- **Items: rated input versus computed output.** The client sends `currentMaturity`, `targetMaturity`, `sensitivity`, `severity`, `likelihood`, text and owner; the server returns `gap`, `exposure` and `riskLevel`, which are read-only. A missing scale keeps all three `null` — that is "not rated", never 0 and never LOW. The same subject (area / requirement / business unit / framework combination) can be rated once per assessment (`409 ASSESSMENT_ITEM_EXISTS`; field errors `unknownArea`, `unknownBusinessUnit`, `unknownFramework`, `unknownRequirement`, `notRequirementFramework`).
- **Summary metrics are coverage objects.** `averageMaturity`, `averageGap`, `averageExposure` and `highOrCritical` are `{ value, assessed, applicable }` with `value: null` when nothing was rated — show "Not assessed", not "0.0". `byRiskLevel` counts only rated items and `notRated` says how many were left out; every summary carries `disclaimer`.
- **Templates are seeded data, read-only.** `GET …/assessment-templates` lists the quick-start packs with `provenance`, `verifiedBy` and `verifiedAt`; there is no create/edit endpoint. `POST …/items/from-template` `{ templateId, version }` is additive: rows whose subject is already in the assessment are skipped (`skipped`), missing governance areas are created and named in `createdAreaNames`, and the answer carries the `disclaimer`. Show all three counts; do not re-fetch the item list to infer them.
- **Priority: the answers, then the quadrant.** `PUT …/assessment-items/{itemId}/priority` sends the **full** answer set `{ answers: { <questionKey>: boolean | null }, version }`; a key you omit becomes unanswered, and any unanswered question means `quadrant: null` (`answersComplete: false` on the list rows). The `version` of a first save is **1** — a client that assumed the row existed gets `409 VERSION_CONFLICT`, which is also what a two-people-opened-the-same-questionnaire race returns. `GET …/priority-matrix` counts the four quadrants and reports `unclassified`, `withoutQuestionnaire`, `totalItems` and `partial` (true when some item cannot be classified) — a `partial` matrix must not be presented as complete.
- **Overrides are an approver's act and are explained.** `…/priority/adjust` (`governance.approve`) sets `urgent`/`important` directly with a **required** `reason` (3–2000); the computed answers stay in the record, `adjusted: true` marks the row and `adjustment` carries who/when/why. `…/priority/clear-adjustment` returns to the computed quadrant and also needs a `reason`. `planWindow.source` is `REFERENCE_DEFAULT` or `ORGANISATION_POLICY`; `schedulingSuggestion` is the sentence the UI shows for "when to do it" — the client must not compute it from `minDays`/`maxDays`.
- **Remediation: the server owns the state machine.** `GET`/`POST …/remediation-tasks` are permission-gated (`governance.view` / `governance.create`), but PATCH and `/status` are open to any active member and then checked against the task: only the assignee or someone with `governance.edit` may work a task, and verifying, reopening and reviving need `governance.approve` — `403 NOT_ASSIGNEE` when neither applies. `GET …/remediation-tasks/{taskId}` returns `allowedTransitions` (`{ toStatus, by, needsReason }`) already narrowed to what **this caller** may do: render the buttons from that array, never from a client-side copy of the table, and require the reason input when `needsReason`. An illegal `toStatus` is `409 INVALID_TRANSITION`. PATCH may clear `dueDate` and `assigneeMembershipId` with `null`; `title` and `priority` cannot be cleared (`400`, codes `isString` / `isIn`).
- **Due dates are computed server-side, in the organisation's timezone.** Rows carry `dueState` = `{ availability, isOverdue, dueDate, asOf }`; `availability: "no_due_date"` means there is nothing to judge, so `isOverdue: false` is not a green light. `?overdue=true` filters on the server's `asOf`, not on the browser clock. `generate` (`{ assessmentId }`) answers `200 { created, skipped, items, skippedItems }` with a reason per skip (`NO_RISK_LEVEL`, `ACTIVE_TASK_EXISTS`) — show the skips instead of re-listing tasks to find them.
- **Evidence has no public URL.** `POST …/evidence` is `multipart/form-data` with field `file` (optional `title`); the size cap is the deployment's `EVIDENCE_MAX_BYTES`, stated by `GET /meta` as `evidenceMaxBytes` (default 4 MiB) and answered with `413` — take the number from there, do not write one into a message. The multipart pipeline bounds the body at 10 MiB whatever the setting, so a value above that is refused at boot. PDF/PNG/JPEG/GIF/text/CSV are detected from the bytes; a `.docx` renamed `.pdf` is `415 UNSUPPORTED_MEDIA_TYPE` because the type that gets stored is the one the bytes proved. A missing or empty part is `400 FILE_REQUIRED`. `GET …/evidence/{id}/download` streams through the API with `Content-Disposition: attachment`, an `ETag` that is the file's `sha256`, `Cache-Control: private, no-cache`, `nosniff` and a locked CSP; send the bearer token, so fetch it with the API client and open a blob URL — a bare `<img src>` or link will 401. `Content-Disposition` is exposed by CORS: read it to name the saved file.
- **Reports are rendered now, not later.** `POST …/reports/governance-assessment` `{ assessmentId, businessUnitId?, frameworkId? }` answers 201 with a `READY` `ReportDto` (`size`, `sha256`) — the PDF is already written when the call returns. `GET …/reports/{id}/download` behaves like an evidence download (same headers, `304` on `If-None-Match`). A report shows at most 300 items; what did not fit is counted and named inside the document, so a big assessment still says so. History, the catalogue and the `PENDING`/`FAILED` states arrived with Phase 9a — see "Reports and the audit trail" below.
- **Every action is audited with the change**: answers, overrides, assessment lifecycle moves, task creation/edits/status/comments, evidence upload and linking, report generation and download. The client sends no audit fields.

## Registers (Phase 6, contract 0.7.0)

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.7.0) and in the contract (`x-access` / `x-permission`). What the generated types do not say:

- **Migrations are applied to dev (2026-10-18).** The registers migration (`20261017120000_phase6_registers`) went in with `20261016220000_assessment_templates` over a non-pooled `DIRECT_URL`, followed by `npm run db:apply-runtime-role`, so the Phase 6 routes answer normally. On a database that has not been migrated they answer `500`, and the pages keep the same "this workspace is not ready yet" explanation the assessment templates dialog uses — that path stays in the code, because not every deployment is migrated.
- **Two scoring systems; never mix them.** An assessment item is scored by `exposure_v1` (sensitivity × severity × likelihood, 1–125, bands an organisation may customise through `GET …/scoring`). A register risk is scored by `risk_matrix_v1` (**likelihood × severity**, 1–25) and Phase 6 uses the **reference bands for every organisation** (Low 1–5, Medium 6–11, High 12–19, Critical 20–25): the scoring policy has no say in it. Take a risk label from the row's `inherent.level` / `residual.level`, from `byResidualLevel` / `byInherentLevel`, or from a heatmap cell's `level` — never from the exposure bands, and never from a legend you wrote yourself. The row also carries `methodologyId` / `methodologyVersion` so a later change of bands cannot rewrite history.
- **Send the factors; read back the derivation.** A risk POST/PATCH carries `inherentLikelihood`/`inherentSeverity`/`residualLikelihood`/`residualSeverity` (each 1–5 or `null`); `score` and `level` are not sendable — the server derives them and moves the derived pair whenever the factors move. A half-stated pair is legal and simply has no score: the row then counts as `NOT_SCORED` (summary) or `unscored` (heatmap), which is a missing judgement, not a zero. Residual risk may only **reduce** inherent risk: if you send a residual factor without the inherent pair, or one that exceeds its inherent counterpart, the answer is `400` with `residualLikelihood` / `residualAboveInherent` and a sentence to show the user.
- **Acceptance is a ledger entry, not a status a row is edited into.** `POST …/risks/{id}/status` has **no step into `ACCEPTED`** — offering it is `409 INVALID_TRANSITION`, whose `detail` names the statuses this one can become. `POST …/risks/{id}/acceptances` (`governance.approve`) is what makes a risk accepted and returns the whole detail with `acceptanceInForce: true`; withdrawing appends a WITHDRAWN row and **you must say where the risk goes** (`toStatus: OPEN | IN_TREATMENT`) — the server never picks. Accepting a risk that has not stated its inherent pair is `400` (`inherentLikelihood` / `notScored`); a second acceptance is `409 RISK_ACCEPTANCE_IN_FORCE`; CLOSED or TRANSFERRED is `409 RISK_NOT_ACCEPTABLE` (acceptance is about risk carried today); `expiresOn` in the past is `inThePast`; `reviewOn` after the expiry is `afterExpiry`. The ledger list is the one register list that is never paginated (`nextCursor` is always null), newest decision first.
- **Render the risk actions from `allowedTransitions`.** Every risk row carries the steps **this caller** may take now, each with `by` (`work` or `approve`) and `needsReason` — the reopen-out-of-`ACCEPTED` and out-of-`CLOSED` steps are approver-only and demand a `reason`. Do not keep a client-side copy of the table. The status route is open to any active member and then checked per row, so a `403` there is a real answer, not a bug.
- **Five registers, one review vocabulary.** `reviewState` (`ok | due_soon | overdue | not_reviewed`) and `daysRemaining` come from `src/domain/registers/review.ts` on risks (`reviewByDate`) and on RoPA activities, lawful basis records and retention rules (`nextReviewDate`, `lastReviewDate`). A classification level carries only its two dates (`lastReviewDate`, `nextReviewDate`) and no state: it is a catalogue, not something the product tracks. `not_reviewed` means **no date at all**: never render it as on time, never as overdue. The lead window is the reference 30 days, and every state is decided against `asOf` — today **in the organisation's time zone**, not the browser's clock. `reviewIntervalDays` is cadence metadata: nothing in the API will ever turn it into a deadline, so a form must not either.
- **The aggregate endpoints state their availability, and the states mean different things.** `…/risks/summary` and `…/risks/heatmap` are `ok | no_records`; `…/ropa/monitor` adds `not_configured`, which is the honest answer for a register where nobody has approved a due date ("nothing is tracked yet", not "all up to date"). An empty register is never "zero risk". CLOSED risks are excluded from the level and review counts (a closed risk is history, not exposure) while `total` and `byStatus` still cover every row. The heatmap always returns all **25 cells** — empty ones at zero — for one basis (`?basis=residual|inherent`, default `residual`); never plot the two bases together. `risk.top` (ordering by exposure, drill-down) is **Phase 8 work** and is not in this contract. Since 0.12.0 the RoPA monitor also counts traceability over the same live rows — `linkedToLawfulBasis`, `linkedToClassification`, `unlinked` (neither) — because a page of the register cannot answer a question about the whole of it: do not re-count `lawfulBasisRecords` client-side and call it the register's coverage.
- **Nothing in Phase 6 deletes.** Levels, activities, basis records and rules are archived; holds are released; the disposal log and the acceptance ledger only grow. `POST …/archive` is refused with `409 RECORD_IN_USE` while a RoPA activity, basis record, rule or evidence still points at the level or rule, and with `409 LEGAL_HOLD_ACTIVE` while a hold covers it (the `detail` is plain language — show it). Archived rows come back only with `includeArchived=true` (or `status=ARCHIVED` on RoPA), and an archived record refuses edits and reviews with `409`. RoPA archive and unarchive are idempotent and a **restore returns `DRAFT`**: nobody resumes an archived activity without looking at it. An omitted classification `rank` appends at the end, and a rank an archived level once held is never handed out again (`409 CLASSIFICATION_RANK_TAKEN`).
- **A legal hold is an approver's act and beats every intention.** `POST …/retention/holds` needs `governance.approve`, not a `data.*` key, so the button belongs in the approver UI. `coveredKind` and `coveredRecordId` come as a pair (`400` with `kindAndRecord` when only one is sent) and the record must belong to this organisation; **no kind at all** means the hold covers the whole rule. `POST …/retention/holds/{id}/release` (`{ reason, version }`) is the only write a hold ever takes, and releasing a released hold returns it unchanged. `POST …/retention/disposals` records that a disposal was carried out — it deletes nothing — and answers `409 DISPOSAL_BLOCKED_BY_HOLD` while any hold covers the rule. There is no hold counter on a rule: read `…/retention/holds?state=live`, or the rule detail's `holds` and `recentDisposals` (the last 20).
- **A lawful basis is approved by its own verb, with a name behind it.** `reviewStatus` is **not** patchable — `POST …/lawful-basis/{id}/review` is the only way to `APPROVED` (`governance.approve`, and the record must carry a `justification`, from that request or its own: `400` with `justificationRequired`); taking an approved basis back needs `governance.approve` and a `reason`; anything the transition table does not allow is `409 INVALID_TRANSITION`. Article 6 has exactly six bases and the list is closed. Evidence linking here and on RoPA is `{ evidenceId }` with **no `version`** (a link is not an edit of the record — unlike an assessment item, which does send one), an unknown evidence id is `404`, linking twice is not an error, and unlink is idempotent; both return the detail.
- **The RoPA side of that link states a basis, it does not edit one** (0.12.0). Every activity response carries `lawfulBasisRecords[]` — `{ id, basis, purpose, reviewStatus }`, oldest link first, empty when nobody has justified the processing. `POST …/ropa` takes an optional `lawfulBasis` (one of the six kinds) and `POST …/ropa/{id}/lawful-basis` takes `{ basis, purpose? }`; both **create a DRAFT record** in the Lawful Basis Register pointing at the activity, in the same transaction as the activity for the create. `purpose` falls back to the activity's own purpose and then its name, so the record is never an empty row. `DELETE …/ropa/{id}/lawful-basis/{recordId}` clears the pointer and leaves the record where it is, exactly as detaching evidence leaves the file; neither route takes a `version`, and both answer the whole `RopaActivityDetailDto`. The shape is a **list** because an activity can be justified on more than one ground — a payroll line is `LEGAL_OBLIGATION` and `CONTRACT` at once — so the sample's single select is a choice of which basis to state, not the contract's shape. Approving what was just created is still the Lawful Basis screen's work: a DRAFT basis is a claim, not a decision.
- **The register's four cards are the server's counts.** `GET …/ropa/monitor` answers `total`, `linkedToLawfulBasis`, `linkedToClassification` and `unlinked` (neither) over the live rows, alongside the review buckets. Do not derive them from the page the table holds: the table is a cursor page of a register that may be longer, and `unlinked` is the figure the register is judged on.
- **Tables need no extra calls.** Rows carry the joined names the UI shows: `governanceAreaName`, `requirementRef`, `businessUnitName`, `ownerName` on risks; `classificationLevelName` + `classificationLevelRank`, `retentionRuleName`, `businessUnitName`, `ownerName` on activities; `processingActivityName`, `ownerName` on basis records; `classificationLevelName`, `ownerName` on rules; `decidedByName` on ledger rows, `placedByName` / `releasedByName` on holds, `createdByName` + `ruleName` on disposals. They are `null` when the reference is empty — that is "not set", not a missing field to chase.

## Incidents and rights (Phase 7, contract 0.8.0)

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.8.0) and in the contract (`x-access` / `x-permission`). What the generated types do not say:

- **Migrations are applied to dev (2026-10-18).** The incidents migration (`20261017180000_phase7_incidents_rights`) went in after `20261016220000_assessment_templates` and `20261017120000_phase6_registers` over a non-pooled `DIRECT_URL`, followed by `npm run db:apply-runtime-role`, so the Phase 7 routes answer normally. On a database that has not been migrated they still answer `500`, and the four pages keep the same "this workspace is not ready yet" explanation rather than presenting it as a client error — that path stays in the code.
- **One deadline vocabulary, three places.** `DeadlineViewDto` is `{ state, dueOn, daysRemaining }` and it appears as `deadline` on a DSAR row and a reminder, and as `assessmentDeadline` + `notificationDeadline` on a breach. `state` is `ok | due_soon | overdue | not_configured`; `not_configured` means **no window exists for this record** — render it as "no deadline set", never as on time and never as overdue. `dueOn` and `daysRemaining` are `null` with it, and `daysRemaining` is negative once the day has passed. Every state is decided against the server's `today` — in the organisation's zone — so never recompute one from the browser's clock. A reminder's own `leadDays` is `null` when the organisation's `alertLeadDays` decides the warning instead.
- **Deadlines are data, frozen when the record was written.** A DSAR stores `policyId`, `responseDays`, `baseDueOn` and `dueOn`; a breach stores `policyId`, `assessmentDays`, `notificationDays` and the two dates. **PATCHing `…/deadline-policy` never rewrites an open record**, so a table cannot show a date that the row's own policy did not produce. The API ships no statutory number: a window exists only because someone set one, which is what `configured` on the policy and `not_configured` on a row both mean. A record with no window queues no alerts.
- **An extension is a ledger entry, and the client never chooses the days.** `POST …/dsar/{requestId}/extension` sends `{ reason, version }` only; the length is the policy's `dsarExtensionDays` and the new date is the request's own frozen `dueOn` plus them — never a recomputation from today's policy. `422 EXTENSION_NOT_ALLOWED` names the block in `errors[0].code`: `terminal_status`, `no_due_date`, `no_extension_policy`, `limit_reached` (the request has used its `dsarExtensionLimit`). Show the block, do not pre-compute whether an extension is possible.
- **Closure is a decision with proof behind it.** Status steps come from the transition table: render the buttons from `allowedTransitions` on the row (`by: 'work'` needs `data.edit`, `by: 'approve'` needs `governance.approve`), never from a client copy; an illegal step is `409 INVALID_TRANSITION` whose `detail` names the statuses this one can become. COMPLETED and REFUSED need a `note` and **an attached evidence row**; COMPLETED additionally needs the identity proven — `422 IDENTITY_NOT_VERIFIED`, which is a prompt to call `POST …/identity` first, not a bug. A terminal request refuses PATCH with `409 RECORD_ALREADY_CLOSED`, and so does a settled reminder. A breach refuses to close without a recorded notification decision — `422 BREACH_DECISION_REQUIRED`. Nothing in this phase deletes.
- **The breach duty is answered by the decision, not by a status.** `notificationState` is derived server-side and follows the newest row of the `decisions` ledger (newest first); a client never sends it. One decision names the authority **either** by `regulatorContactId` **or** by `authorityName`, never both, and a REQUIRED decision names a `targetDate`. `notificationSettled` is the flag that says the duty has been read, and it is what makes the notification deadline stop counting as late. `detectedOn` is not editable — the frozen duty dates are checked against it in the database — and containment is a `chronology` kind, not a status.
- **Evidence has versions, and a new one forgets the old verdicts.** `currentVersion` on the row is the one a plain download serves; `GET …/evidence/{id}/download?version=n` names any other (`404 EVIDENCE_VERSION_NOT_FOUND`). PATCH, `/review` and `/scan` all take `version`; a stale number is `409 VERSION_CONFLICT`. Uploading a version resets the review to `UNREVIEWED` and the scan to `NOT_SCANNED` — an unscanned byte-stream cannot inherit another version's verdict — and every version stays downloadable. The version list never carries the storage key. `attestEvidenceScan` cannot attest `NOT_SCANNED` (the absence of a verdict), and `INFECTED` / `UNABLE_TO_SCAN` require a note. There is no scanner in this build: the attested state is what the UI has to show.
- **Reminders alert the assignee; preferences can only silence your own.** `GET …/reminders/preferences` (`notifications.own`) is the signed-in member's own row with `emailDueSoon` / `emailOverdue`, `configured` and `savedAt`; with nothing saved both are **on** — it is an opt-out switch, not an opt-in, and there is no id in the path, so another member's choices are unreachable. Those two switches govern only the two reminder alert kinds: an incident alert to the designated data protection contact is not a preference and cannot be silenced. Moving a `dueOn` re-queues both thresholds for the new day and leaves the old queue rows behind with `STALE_DEADLINE`.
- **The alert ledger answers "was anybody told", and a skip is a row.** `GET …/alerts/deliveries` lists `kind`, `status` (`QUEUED` / `SENT` / `FAILED` / `SKIPPED`), `recordId`, `dueOn`, `skipReason`, `attempts`, `sentAt`, `lastError`, and `recipientAddress` / `recipientLabel` only once a send happened. `skipReason` is one of `NO_RECIPIENT`, `PREFERENCE_OFF`, `STALE_DEADLINE`, `ALREADY_HANDLED` — an absence of a SENT row is not evidence that nothing was due, so show the row. There is no write route for this table.
- **Alert emails are link-only, so the four pages must honour `?open=<recordId>`.** The body names no requester, no breach and no count; the link is `<APP_BASE_URL><page>?open=<recordId>` with `<page>` one of `/dsar-tracker`, `/breach-registry`, `/reminders`. Each page should read `open` on load and bring that record forward (detail dialog or a highlighted row), and clear the parameter afterwards. `recipientLabel` is a ROLE, never a person — that is the text to show beside a recipient column.
- **Two metrics, and both state their own availability.** `GET …/dsar/sla` returns `state` (`not_configured | no_records | measured`), `windowDays`, `records`, `withinSla`, `completedLate`, `openPastDeadline`, `openNotYetDue`, `breached`, `percentage` (one decimal, `null` when nothing has been measured) and `today`; the window is 365 days and requests that are still open and not yet due are counted but never enter the percentage. `GET …/breaches/summary` returns `open`, `annualTotal` (the organisation's own calendar year), `overdue` (notification duties late **and undecided**), `notificationConfigured` and `today` — when that flag is false, nothing can be late, which is a fact rather than an error. Neither endpoint is a compliance statement, and both must be shown with their `disclaimer`.
- **Register text is audited as `'changed'`, and a DSAR's subject details go no further than the row.** The requester's name, email and notes never appear in an audit entry, a job payload, a log line or an email; the audit carries the fact of the change and the decisions (extension reason, status note, notification decision, cancel reason) with the actor's identity behind them. The client sends no audit fields.

Operation names, paths and permissions are in [contracts/CHANGELOG.md](../contracts/CHANGELOG.md) (0.9.0) and in the contract (`x-access` / `x-permission`). What the generated types do not say:

- **The screen is ten calls, not one.** Four are new and organisation-wide (`…/dashboard/summary`, `…/dashboard/frameworks`, `…/dashboard/gap-analysis`, `…/dashboard/top-risks`, all `dashboard.view`); the other sections keep the endpoint of the module that owns their number — the heat map (`…/risks/heatmap`), the register counts (`…/risks/summary`), the RoPA monitor (`…/ropa/monitor`), the priority matrix (`…/priority-matrix`), the DSAR SLA (`…/dsar/sla`) and the breach summary (`…/breaches/summary`). Load each independently and render each in its own state: a section that fails or answers "not assessed" must not blank the page, and there is deliberately **no** `dashboard/heatmap` or `dashboard/ropa` variant to call. A second copy of a count is a second definition waiting to disagree with the first.
- **Every measured figure is a coverage triple.** `MeasuredDto` is `{ value, assessed, applicable }`, and `value: null` means "no number exists to show" — render it as `Not assessed`, never as `0`, `0 %`, `—` or a verdict. `assessed` and `applicable` are usually different (`applicable` is the size of the subject set, `assessed` how many of them carry that side), and `current`, `target` and `gap` each have their own denominators, so a progress bar drawn from `assessed / applicable` and a mean taken over `value` are two honest facts, not one to reconcile.
- **Read the availability word before the number.** `maturity.availability` is `ok | not_assessed`; `exposure.availability` adds `no_records` (nothing has been submitted or approved yet) and `unable_to_calculate`; `frameworks.availability` is `ok | not_configured` with a `message` to show; a framework row is `ok | not_assessed`; `gap-analysis` is `ok | not_assessed`; `top-risks` is `ok | no_records`. `status` (`compliant | needs_attention | in_progress`, else `null`) is only meaningful when `availability` is `ok` — a null status is not a bad status. Label `compliant` as **"Meets target"** and never render an unassessed framework as "Non-compliant".

Never blend the numbers client-side to produce a gauge.
- **The highlight gap comes from the payload.** `gapHighlightLevels` (summary, frameworks) and `highlightAt` (gap analysis) are the server's number, and each gap row carries its own `highlight` flag. Do not hard-code 2: the day the threshold changes, the screen and the PDF have to change together, and they can only do that if both read it.
- **`asOf` is the day every state was decided, in the organisation's zone.** All four payloads return `asOf` (date-only) and `timezone`. Show "Position as of …" with the value the server sent, and never recompute `overdue`, `due soon` or a calendar year from the browser's clock — the register pages, the DSAR card and the PDF would then tell three stories about one date.
- **`top-risks` answers the heat map's question, and the drill-down goes back to the register.** `basis` is `residual` (default) or `inherent` — the same word `…/risks/heatmap` takes — and `limit` defaults to 10 and is capped at 25. Each row carries its own `score`/`level`/`likelihood`/`severity` for the basis asked, and `null` for the ones it has no pair for; `ownerName`, `businessUnitName`, `frameworkCode`, `governanceAreaName`, `reviewByDate`, `nextAction` and `task` are all nullable because the register lets a risk be filed without them. `unscored` counts the carried risks this list cannot rank — show it, or a short list looks like the whole register. A cell links to `…/risks?basis=<the cell's>&likelihood=<1-5>&severity=<1-5>&includeClosed=false` (the grid plots only risks that are still carried), so the drill-down is the register page's own table, with its own filters, cursor and columns.

The titles, descriptions and completion come from the server (the PDF prints the same words); a link should point at the page that makes the step true. Dismissing the panel hides it — there is no endpoint for it and no state to send, and hiding it cannot mark anything complete.
- **The AI card is honest about not existing.** `POST …/dashboard/ai-assessment` (`ai.run`, no body) answers `503` with `code: "FEATURE_UNAVAILABLE"` until Phase 10. Show its `detail` as the reason; do not retry, queue or back off — that code means "not built", not "busy". A caller whose role lacks `ai.run` gets `403` first, so hide the action the way the rest of the app hides an action the role does not allow.
- **The PDF is generated in the request, and the bytes are only ever downloaded through the API.** `POST …/reports/executive-dashboard` (`reports.export`, no body) returns the finished `ReportDto` with `status: "READY"`, `template: "executive_dashboard"` and `assessmentId: null` (the document spans the organisation). Fetch the file with `GET …/reports/{reportId}/download` (`reports.view`) as a bearer-authenticated request so the response headers can be honoured for the filename — a plain `<a href>` cannot carry the token. `size` and `sha256` describe the stored bytes, and re-reading `GET …/reports/{reportId}` is how the client checks the record still exists. The async path Phase 9a adds is the exception, not this call: see "Reports and the audit trail" below.

A score is not a legal verdict, and the client should not paraphrase that into its own sentence.

## Reports and the audit trail (Phase 9a, contract 0.11.0; the RoPA register document in 0.12.0)
- **The catalogue builds the form; nothing is hard-coded.** `GET …/reports/catalogue` (`reports.view`) returns `items` — every template this build renders, with `template`, `version`, `title`, `description`, `generate` (`sync` \| `async`), the `permission` that generates it and `params[]` (`name`, `type` `uuid \| enum \| boolean`, `required`, `values`, `default`) — and `planned` (`template`, `title`, `phase`). Render the option lists from `values` (the DPO period presets belong to the server), show a planned template as "planned for phase 9b" rather than hiding it, and hide the Generate button when the caller's `permissions` (from `GET …/organisations/:id/me`) lack the row's `permission`. The catalogue is static reference data: it reads no rows, so it never tells a different story per tenant.
- **`generate` decides the whole interaction.** A `sync` template answers `201` with a `READY` record — the PDF already exists, offer it immediately. `POST …/reports/consolidated-dpo` (`reports.export`, body `{ period?, confidential? }`) answers `202` with a **`PENDING`** record whose `size` and `sha256` are `null`: that is not a failure, it is a document that has not been drawn yet.
- **The RoPA page's Export PDF is a third synchronous document** (0.12.0). `POST …/reports/ropa-register` (`reports.export`, no body) returns the finished `ReportDto` with `template: "ropa_register"` and `assessmentId: null`, and the bytes come from the same download route as every other report — nothing new to build, and nothing to poll. It is the standing register, not a period: it takes no parameters, so the catalogue's `params` for it is an empty list and the form should show no fields. Its figures are `GET …/ropa/monitor`'s, because it reads them through `RopaService`: the PDF and the four cards cannot disagree, and a client must not compute the register's coverage itself and be surprised when the document says otherwise.
- **The poll is `GET …/reports/{reportId}`.** Re-read it while `status` is `PENDING` (a couple of seconds between reads is plenty; the record also appears in the history list). `READY` ⇒ the download works. `FAILED` ⇒ show `errorCode` and `errorDetail` (the stored, sanitised reason) and offer nothing but "try again". A download of a report that is not `READY` answers `409 CONFLICT` whose `detail` says which, so never render a download link for a `PENDING` or `FAILED` row — the server will refuse it and the message will read like a bug.
- **Whether a queued report settles depends on the deployment, not on the client.** Nothing drains the job queue between requests: with the in-process dev runner a DPO report turns `READY` on its own within seconds, while on a function host it stays `PENDING` until something calls the internal tick. A history list full of `PENDING` rows on a deployment with no scheduler is the honest state — say "queued", never "generating…" with a spinner that will never finish.
- **History is a cursor page.** `GET …/reports` (`reports.view`, newest first) filters `template`, `status`, `assessmentId` and `from`/`to` as whole **UTC days** over the moment the report was asked for. `template` accepts the ids the catalogue lists, including ones no longer generated.
- **Report generation needs the Phase 9a migration applied.** Until it is, every generate route answers `500 INTERNAL_ERROR`; the catalogue, the history list and both audit routes are unaffected, because they only read.
- **The audit trail is a search, not a feed.** `GET …/audit` (`audit.view`) is a cursor page, newest first, with `from`/`to` (whole **UTC days** — an audit row is an instant, not a business deadline, so these are not the organisation's calendar), `actorUserId`, `action` (the `AuditAction` catalogue the response also uses), `outcome` (`SUCCESS` \| `DENIED` \| `FAILURE`), `entityType` and `entityId`. `changes` is returned in full here and is **not** searchable; do not build a client-side text box that implies it is.
- **A trail row names no one.** `actorUserId` is an id, `actorType` is `USER` or `SYSTEM`, and `entityLabel` is the name the record had **at the time**. `audit.view` reaches a Compliance Manager while `users.view` does not, so the client must not resolve an actor id into a name or address unless it already legitimately holds the member list — show "System" for `SYSTEM`, the member's name only where the app already shows members, and otherwise the id. The screen's own wording: who did what to which record, and when.
- **CSV export is a bearer fetch, not a link.** `GET …/audit/export` (`audit.export`) takes the same filters and answers `text/csv` with `Content-Disposition`; read the filename from that header (the app already does this for evidence and report downloads) rather than inventing one. A period holding more than 5,000 events is refused with `422 EXPORT_RANGE_TOO_LARGE` — the message is "narrow the period", and there is no partial file to accept. In the file, `changes` is cut at 1,000 characters and marked `[truncated]`; the list endpoint has the full values.
- **Nothing in the trail can be edited.** There is no write route for anyone, and the API will not accept one; a UI that offers "correct this entry" is describing a feature that does not exist and must not exist.
