# Metric definition sheet

Every number or state shown on the dashboard (and in reports) has a definition here **before** it is built. A metric ships with: this sheet entry, golden tests (empty, partial, full, edge), and an `availability`/`status` result that never turns missing data into a value. Rules: `.claude/skills/grc-domain/SKILL.md`. Definitions below are **drafts**; each is finalised and tested in the phase that builds its module (column *Phase*), then the dashboard (Phase 8) composes them.

## Template (copy for each metric)
| Field | Content |
|---|---|
| Key | `domain.metric` (stable; used as `definitionKey` in API responses) |
| Definition | exact formula in words and maths |
| Scope | organisation; optional filters (framework, business unit); which records and statuses count |
| Period | as-of time, window, and timezone (the organisation's) |
| Inputs | tables/columns, methodology id + version |
| Missing-data rule | what is excluded; when the result is `not_assessed`, `no_records`, `not_configured`, `unable_to_calculate` |
| Result | `{ availability, status, value, coverage, asOf }` with units |
| Access | permission required to see it |
| Tests | golden fixtures: none, partial, full, edge |

## States (shared vocabulary)
- `availability`: `ok | not_configured | not_assessed | no_records | unable_to_calculate`
- `status` (only when `ok`): `in_progress | compliant | needs_attention | overdue | null`. The UI labels `compliant` as **"Meets target"**.

## Metrics
| Key | Definition (draft) | Missing-data rule | Phase |
|---|---|---|---|
| `maturity.overall` | Mean `current_maturity` over **assessed** items of the organisation's applicable framework versions (latest submitted/approved revision per control), equal weight. Value `x / 5` (2 dp); coverage `{assessed, applicable}`. Status: `compliant` if every assessed item has current ≥ target; `needs_attention` if any assessed gap ≥ 2 (configurable); else `in_progress`. | unassessed excluded; none assessed ⇒ `not_assessed`; no framework applicable is stated by `frameworks.coverage` as `not_configured` — the maturity figure itself is `ok` or `not_assessed` | 5/8 |
| `maturity.byFramework` | Same mean per **applicable** framework, over that framework's subjects in the organisation's current answers, with assessed/applicable counts, mean target, gap bands and the outstanding-task count. Measured against the newest `VERIFIED`/`PUBLISHED` version of the framework, whose control count is the denominator of "how big is it". | a framework with zero assessments is `not_assessed` (never 0 %, never "non-compliant"); no version loaded ⇒ no control count is stated (`catalogueControls: null`) | 5/8 |
| `gap.analysis` | Per **governance area**: current, target, `gap = target − current` (levels), mean exposure and item count, from the organisation's current answers. Sorted by mean gap desc, then exposure desc, then area name — an unmeasurable row never leads. Highlight gap ≥ threshold (`gapHighlightLevels` / `highlightAt`, default 2, always stated by the server). Subjects with no area are one row named in words, not dropped. | `gap = null` when either side is null; no row has a gap ⇒ `not_assessed` | 5/8 |
| `risk.exposure.overall` | Mean `exposure_v1` score over the organisation's current-answer subjects; category = band of the mean under the organisation's bands **in force today** (this figure is the position now, not a signed document's); methodology id and version shown. The risk-register summary (`risk_matrix_v1`, residual) is a **separate** metric on its own endpoint. | none assessed ⇒ `not_assessed`; no eligible cycle ⇒ `no_records`; the set spans more than one methodology ⇒ `unable_to_calculate`, which names the methodologies — two band sets never make one average | 5/8 |
| `risk.heatmap` | Count of **open** (not Closed) register risks per `(likelihood, severity)` cell of the 5×5 `risk_matrix_v1` grid, all 25 cells always present; `basis=residual` (default) or `inherent`; each cell drills down to its risks in the dashboard. A risk whose pair is incomplete is counted in `unscored`, never placed. | empty register ⇒ `no_records` (never "zero risk") | 6/8 |
| `risk.review.outstanding` | Risks that need a look: `overdue` (review date before today), `dueSoon` (within the 30-day reference lead), `ok`, `notScheduled` (no review date at all), counted over the risks that are not CLOSED, against today in the organisation's zone. | a missing review date is `notScheduled` — never overdue, never on time | 6/8 |
| `risk.top` | Top N (default 10, maximum 25) carried risks by the exposure score **their own register rows store**, on `basis=residual` (default) or `inherent` — the heat map's own word, so a grid and a list agree. Tie-breakers: severity desc, then earliest `reviewByDate` (an unscheduled risk is neither soonest nor never), then name. Each row carries its level, the two factors of that basis, the owner, business unit / governance area / framework code, the register's next action and the oldest outstanding task filed against its item. | no carried risk ⇒ `no_records`; a risk with an incomplete pair on this basis cannot rank, so it is counted in `unscored` and named there rather than quietly placed last | 8 |
| `priority.quadrants` | Counts of governance areas/tasks per quadrant (Do Now, Plan, Delegate, Eliminate) from saved answers under a ruleset version; items without a completed questionnaire are reported as `unclassified`, not hidden. | unanswered ≠ No | 5/8 |
| `ropa.monitor` | Processing activities by review state over the live (non-archived) records: `overdue` (due date before today), `dueSoon` (within the record's `reviewLeadDays`, or the 30-day reference lead when it says nothing), `onTrack`, `notReviewed` (no approved due date). `asOf` is today in the organisation's zone. | zero activities ⇒ `no_records` ("No records yet", never "all up to date"); **no due date on any record ⇒ `not_configured`** — a register nobody has given a deadline to is reported as such, and `reviewIntervalDays` is never used to invent one | 6/8 |
| `retention.holds.active` | Legal holds that are live (placed, not released), split by what they cover: a whole retention rule or one named record (`EVIDENCE`, `ROPA_ACTIVITY`, `LAWFUL_BASIS_RECORD`, `RETENTION_RULE`). A live hold is what makes a disposal claim impossible. | none ⇒ the list is empty and no disposal is blocked | 6/8 |
| `dsar.sla` | Over requests received in the window (default last 12 months): `withinSla` = completed on/before deadline; `breached` = completed late + open past deadline; `openNotYetDue` is reported **separately** and excluded from the percentage. Percentage = `withinSla / (withinSla + breached)`. Status `overdue` if any open request is past its deadline. | no deadline policy ⇒ `not_configured`; denominator 0 ⇒ `no_records` | 7 |
| `breaches.open` | Count of breaches not Closed; `annualTotal` = breaches detected in the current calendar year (organisation timezone). Status `overdue` when a configured notification deadline has passed without a recorded decision. | none ⇒ `no_records` | 7 |
| `frameworks.coverage` | Per applicable framework: subjects in scope and how many carry a maturity (assessed vs the newest usable version's control count), the mean current/target/gap, the gap-band distribution (`met`, `minor`, `major`, `unmeasured`) and the outstanding findings — remediation tasks filed under that framework whose status is `OPEN`, `IN_PROGRESS` or `BLOCKED`. One payload feeds the comparison bar, the radar, the table and the compliance cards, so those views cannot disagree. | coverage 0 ⇒ `not_assessed`; no applicable framework at all ⇒ the endpoint answers `not_configured` with a `message`; **never** labelled "Non-compliant" | 5/8 |
| `onboarding.progress` | Six steps derived from saved data on every read: `companyDetails` (name, country **and** DPO email all filled in), `businessUnits` (≥ 1), `submittedAssessment` (≥ 1 cycle submitted or approved), `ropaRecords` (≥ 1 activity), `classifiedData` (≥ 1 activity carries a classification level), `mappingReviewed` (frameworks declared applicable **and** ≥ 1 mapping approved). `completed / total`; the wording comes from the server so the screen and the PDF say the same thing. Dismissing hides the panel but never marks a step complete. | derived, never stored as a flag — there is no "step done" column for anybody to tick | 3–8 |

## Golden-test fixtures (each metric)
`empty` (no records, nothing configured) · `configured-but-empty` · `partial` (some assessed) · `full` · `edge` (all overdue, nothing due yet, boundary dates around midnight in the organisation timezone, single record). Expected `availability/status/value/coverage` live next to the test.

## What Phase 5 built (contract 0.6.0)

Phase 5 ships the **inputs** for the rows above, scoped to a single assessment; the organisation-wide `availability`/`status` wrappers are finalised when the dashboard composes them (Phase 8).

- `GET …/assessments/{assessmentId}/summary` → `averageMaturity`, `averageGap`, `averageExposure` and `highOrCritical` as coverage objects `{ value, assessed, applicable }`, with `value: null` when nothing was rated, plus `byRiskLevel`, `notRated`, `itemCount` and the `disclaimer`. It covers the assessment scope of `maturity.overall`, `gap.analysis` and `risk.exposure.overall`; the mean is taken over **rated** items only, and the rating snapshot is the assessment's own frozen bands.
- `GET …/priority-matrix` → the `priority.quadrants` counts under ruleset v1: per-quadrant counts, `unclassified`, `withoutQuestionnaire`, `totalItems` and `partial`. An unanswered question is never read as "No" and never counted in a quadrant.
- Remediation **workload** is not a stored counter: `GET …/remediation-tasks?overdue=true` and each row's `dueState` (computed in the organisation's timezone, `asOf` returned) are what a card or a report uses. `frameworks.coverage`'s "outstanding findings" is therefore `listRemediationTasks` filtered to `OPEN`, `IN_PROGRESS`, `BLOCKED`.
- **No golden fixtures are committed for these** (owner decision: no new automated tests in Phase 3, 4 or 5). The rules live in `src/domain/scoring` and `src/domain/remediation/policy.ts`, which are pure and take effect through the endpoints above; adding the golden tests is Phase 11 work.

## What Phase 6 built (contract 0.7.0)

Phase 6 ships the registers these metrics read from, and the endpoints that return the counts already decided on the server. The organisation-wide `availability`/`status` wrappers are finalised when the dashboard composes them (Phase 8).

- `GET …/risks/summary` → the `risk.review.outstanding` buckets (`reviews.overdue`, `dueSoon`, `ok`, `notScheduled`) plus `byStatus`, `open`, `byResidualLevel` and `byInherentLevel` (each `LOW`…`CRITICAL` **plus `NOT_SCORED`**), `total` over the risks that are not CLOSED, `acceptancesExpiring` (an acceptance whose expiry is today, past, or inside the 30-day lead) and `asOf`. `availability` is `ok` or `no_records`: an empty register is never "zero risk", and a risk without a complete factor pair is counted as not scored rather than dropped.
- `GET …/risks/heatmap?basis=residual|inherent` → the `risk.heatmap` counts as all 25 cells of the 5×5 grid (`{ likelihood, severity, count, level }`, empty cells at zero, each level from the same reference bands the rows carry) plus `unscored`, `availability` and `asOf`. The two bases are never mixed in one response, and CLOSED risks are not plotted — a closed risk is history, not exposure.
- `GET …/ropa/monitor` → the `ropa.monitor` buckets over live activities with `availability` `ok` / `no_records` / `not_configured`. **`not_configured` is the decision the earlier draft of that row did not make**: a register where nobody has approved a due date is reported as not configured, not as "all up to date", because `reviewIntervalDays` is cadence metadata and inventing a deadline from it would put a date on a record that no person stood behind.
- Retention exposure is read from `GET …/retention/holds?state=live` (the `retention.holds.active` list, each with the rule it covers and whether it is blanket or record-specific) and `GET …/retention/disposals` (the append-only log). There is no "hold count" field on a rule: a live hold is a fact the disposal route checks inside the transaction, and `409 DISPOSAL_BLOCKED_BY_HOLD` is what a blocked claim looks like.
- Every review state in Phase 6 comes from `src/domain/registers/review.ts` — the same four states, the same 30-day reference lead, the same "today in the organisation's zone" — so a risk, a processing activity, a basis record, a classification level and a retention rule cannot disagree about what `overdue` means. The dashboard's cards are the counts above, not recomputed ones.
- `risk.top` is **not built here** (Phase 6 row): Phase 6 gives the register list with its filters (`status`, `category`, `businessUnitId`, `governanceAreaId`, `ownerMembershipId`, `reviewDueBy`, `q`) and the two aggregate views; ranking by exposure and drilling a heat-map cell down into its own risks is Phase 8 work, and Phase 8 built both.
- **No golden fixtures are committed for these** (owner decision: no new automated tests in Phase 3, 4, 5 or 6). The rules live in `src/domain/risk/policy.ts` and `src/domain/registers/`, which are pure, and are enforced a second time by the database CHECKs and triggers of `20261017120000_phase6_registers`; adding the golden tests is Phase 11 work.


## What Phase 7 built (contract 0.8.0)

Phase 7 builds the two metric rows whose *Phase* column says 7 — `dsar.sla` and `breaches.open` — plus the records, the deadline policy and the alert ledger every other incident card will read from. The organisation-wide `availability`/`status` wrappers are finalised when the dashboard composes them (Phase 8).

- `GET …/dsar/sla` → `dsar.sla` as `{ state, configured, windowDays, records, withinSla, completedLate, openPastDeadline, openNotYetDue, breached, percentage, today }`. `state` is `not_configured` when no response window is in force, `no_records` when the denominator is empty, `measured` otherwise — an empty window and an empty register are deliberately the same "nothing was counted" answer, and neither is 0 %. `openNotYetDue` is a count of its own and is **not** in `percentage`, which is `withinSla / (withinSla + breached)` to one decimal (`breached` = `completedLate` + `openPastDeadline`). A `REFUSED` or `WITHDRAWN` request is bucketed `notMeasured`: the definition counts a request as answered when it was **completed**, and adding a refusal to either side of the fraction would invent a rule the sheet does not state — it is still counted in `records`, so nothing is dropped. `today` is the organisation's calendar day every bucket was decided against, and the window is the last 365 days of `receivedOn` — what the row's "default last 12 months" is realised as, fixed on the server rather than a query parameter a report could drift against.
- `GET …/breaches/summary` → `breaches.open` as `{ open, annualTotal, overdue, notificationConfigured, today }`: `open` counts the statuses that are not CLOSED, `annualTotal` counts what was detected in the organisation's current calendar year (closed ones included — it is what happened that year), and `overdue` is specifically the breaches whose **notification** duty is late: an undecided one past its date, since a recorded decision answers the duty however the fix is going. `notificationConfigured` is false when no notification window exists, in which case nothing can be late and no date was invented.
- **The deadline policy is the input both metrics share** (`GET/PATCH …/deadline-policy`): one row per organisation, every column nullable, no reference default anywhere. `configured` is false when nothing is set, and a record created while its window was unset carries `responseDays: null` / `dueOn: null` forever — that is `not_configured` on the record, the list and the SLA, never "on time". Changing the policy never rewrites an open record: the numbers and the dates in force at creation are frozen on the row, and an extension moves the date only through the append-only ledger, which the database checks adds up.
- `GET …/alerts/deliveries` → the delivery ledger any "N alerts sent / M skipped" card reads: one row per record, threshold and date, with `status` (`QUEUED`/`SENT`/`FAILED`/`SKIPPED`), `skipReason` (`NO_RECIPIENT`, `PREFERENCE_OFF`, `STALE_DEADLINE`, `ALREADY_HANDLED`), the recipient address and role label, `attempts` and `sentAt`. **A skip is a row, not an absence**, so a card can distinguish "nothing to report" from "the member asked not to be emailed" — the two are different facts and an empty count would erase the difference.
- The four incident lists each carry their own deadline view (`state`, `dueOn`, `daysRemaining`) on every row, computed once in `src/domain/incidents/deadline.ts` against today in the organisation's zone. A card counts those; it does not recompute them, which is why a DSAR row, a breach duty, a reminder and an evidence review cannot tell four different stories about the same date.
- **No golden fixtures are committed for these** (owner decision: no new automated tests in Phase 3, 4, 5, 6 or 7). The rules live in `src/domain/incidents/`, which is pure, and are enforced a second time by the database CHECKs and triggers of `20261017180000_phase7_incidents_rights`; adding the golden tests is Phase 11 work. The `dsar.sla` and `breaches.open` rows above are the definitions those tests will be written against.


## What Phase 8 built (contract 0.9.0)

Phase 8 composes the organisation-wide `availability`/`status` wrappers the earlier sections deferred, in four endpoints under `dashboard.view`, and it does it **without taking a second copy of any number that already has an owner**: the rows whose *Phase* column says `6/8` or `7` are still read from their own endpoints. `docs/metrics/README.md`'s own rule — "the dashboard's cards are the counts above, not recomputed ones" — is the reason `GET …/risks/summary`, `…/risks/heatmap`, `…/ropa/monitor`, `…/priority-matrix`, `…/dsar/sla` and `…/breaches/summary` keep answering for themselves, and why `overdue` cannot mean two things on one screen.

- **The eligibility rule is realised once**, in `src/domain/dashboard/metrics.ts`, and every `/8` row above quietly depends on it: only a cycle in `IN_REVIEW` or `APPROVED` is the organisation's finding (a `DRAFT` is work in progress, a `SUPERSEDED` one is the older revision of work since re-signed); a *subject* is a requirement, or a governance area for one business unit, or an ad-hoc item that never replaces another; and per subject the organisation's current answer is the item from the **newest** eligible cycle — approval instant, else submission, else creation, ties broken on the cycle's creation date and then its id (UUIDv7, so id order is creation order). That is this sheet's "latest submitted/approved revision per control", and it is a single function rather than four SQL dialects.
- `GET …/dashboard/summary` → `maturity.overall`, `risk.exposure.overall` and `onboarding.progress` as `{ asOf, timezone, gapHighlightLevels, maturity, exposure, gettingStarted, disclaimer }`. `maturity` is `ok | not_assessed` with `current`/`target`/`gap` as `{ value, assessed, applicable }` each and `applicable` the size of the subject set — a mean is taken over the subjects that carry that side, so the three coverage pairs can have different denominators and none of them is a zero. `status` is `compliant` only when every subject with both sides already meets its target, `needs_attention` as soon as one is short by `gapHighlightLevels`, `in_progress` in between, and **null when nothing is rated**: an unassessed register is not a verdict. `exposure` adds `no_records` (no eligible cycle at all) and `unable_to_calculate` — the decision this sheet's "never mixed across methodologies" demanded: when the counted subjects span more than one `methodologyId@version`, the response names those methodologies, gives no mean, no band and no `byRiskLevel`, and says it cannot merge two band sets into one average. The band of the mean is the organisation's policy **in force today**, because the dashboard is the position now, not a signed document's.
- `GET …/dashboard/frameworks` → `frameworks.coverage` and `maturity.byFramework` per framework the organisation holds as applicable, as `{ availability, asOf, gapHighlightLevels, frameworks[], message, disclaimer }`. `availability` is `not_configured` when none is applicable — with a `message` in the reader's language, and an empty list that is *explained* rather than rendered as "no coverage". Each row is measured against the newest `VERIFIED`/`PUBLISHED` version of that framework and carries `catalogueControls` (null when no usable version is loaded: no denominator can be stated), `inScope`, `rated`, the three coverage pairs, `gapBands { met, minor, major, unmeasured }`, and `outstandingFindings` = the tasks filed under that framework whose status is `OPEN`, `IN_PROGRESS` or `BLOCKED` — this row's "outstanding findings", which is why it was never a stored counter. `unmeasured` counts a subject with a missing side instead of dropping it. One payload feeds the comparison bar, the radar, the table and the compliance cards, so those four views cannot disagree, and a framework nobody has rated says `not_assessed` — never 0 %, never "Non-compliant".
- `GET …/dashboard/gap-analysis` → `gap.analysis` per governance area: `{ availability, asOf, highlightAt, rows[], disclaimer }`, each row with its own item count, the three coverage pairs, mean exposure, `highlight` (its mean gap reaches `highlightAt`) and `status`. Ordered by mean gap desc, then exposure desc, then area name, with **an unmeasurable row never leading**; subjects with no area are their own row, named in words ("Not filed under a governance area"), not hidden. `availability` is `not_assessed` unless at least one row can state a gap.
- `GET …/dashboard/top-risks?basis=residual|inherent&limit=` → the `risk.top` row this sheet said was "not built in Phase 6". `basis` is the heat map's own word, and the list ranks the exposure score **its register rows already store** — `residualScore`/`residualSeverity` or the inherent pair — so a cell and a card agree. Tie-breakers exactly as the row states: severity desc, then the earliest `reviewByDate` (a risk with no next-action date is neither "soonest" nor "never", so it ranks last on that key), then name; an unscored risk cannot rank above a scored one and is counted in `unscored` instead of quietly placed last. Each row carries its level, the two factors of the basis, the owner's name, the business unit / governance area / framework code it is filed under, the register's `nextAction`, and `task` — the **oldest** outstanding task filed against its item, chosen in one set-based read so the same risk points at the same task on every reload. `limit` defaults to 10 and is capped at 25; `availability` is `no_records` when nothing is carried. CLOSED risks are not ranked: a closed risk is history.
- **The heat map's drill-down became filters, not a route**: `GET …/risks` gained `basis`, `likelihood` and `severity`, and `src/risks/risks.repository.ts` reads exactly the factor pair of the basis named. Clicking a cell asks the register for its own risks, so the count in the grid and the length of the list are one query, and there is no second implementation of "which risks are in this cell".
- `POST …/reports/executive-dashboard` (`reports.export`) renders the one-page PDF **from these payloads** — `summary`, `frameworks`, `gap-analysis`, `top-risks` — so the printed figure and the screen figure cannot diverge; the record's `dataSnapshot` holds what was printed and `ReportParamsDto.assessmentId` became nullable because this report spans the organisation. Its scope is a decision: the sections owned by another module (the DSAR SLA, open breaches, the RoPA monitor, the priority matrix) are live cards on the screen and belong to the Consolidated DPO Report (Phase 9a), not to this document.
- `POST …/dashboard/ai-assessment` (`ai.run`) answers `503 FEATURE_UNAVAILABLE` until Phase 10 builds `src/ai`. The code is new and deliberately distinct from `SERVICE_UNAVAILABLE`: the server is healthy and retrying changes nothing, so a client must not queue the call again — while the endpoint exists so the screen can show the action and a **true** reason for its absence. Nothing is generated, stored or queued, and no prompt runs against this organisation's data.
- Every read is **one unit of work** of set-based queries — no query per card and none per row — and `asOf`/`timezone` are returned by all four endpoints, so a date a card decides against is stated rather than guessed from the browser's zone. `gapHighlightLevels`/`highlightAt` travel in the payload for the same reason: the screen and the report highlight the same rows.
- **No new permission key** is introduced (`dashboard.view` and `ai.run` both existed), so `docs/rbac-matrix.md` and its parser test are unchanged by this phase.
