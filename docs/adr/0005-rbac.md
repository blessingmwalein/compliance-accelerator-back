# ADR-0005: Role-based access control (six roles) and platform administration

- **Status:** Accepted and **implemented in Phase 2c**; the platform-admin flag is still an **assumption to confirm**
- **Date:** 2026-10-14

## Context
The legacy code defines six roles; its in-app manual describes a different six (Admin, DPO, Compliance Officer, Auditor, Assessor, Read-only Executive). The owner chose the **code's six**: Company Owner, Company Admin, Compliance Manager, Course Administrator, Standard User, Read Only.

## Decision
- Roles are fixed system roles in v1; each is a bundle of `module.action` permissions from a typed catalogue (`view/create/edit/delete` plus `approve/export/assign/manage`). The legacy matrix is the baseline; new keys are additions flagged in [rbac-matrix.md](../rbac-matrix.md). The catalogue is emitted as OpenAPI `x-permission`.
- Authorisation is enforced server-side by global deny-by-default guards (`@RequirePermission` / `@Public` / `@PlatformOnly`); record-level rules use `@Policy`. No business-unit-scoped access in v1 (extension point only). **CASL rejected** for now (Prisma 7 compatibility unverified; custom guards suffice).
- The **DPO is a designated contact** on the organisation (not a role); breach and DSAR alerts go to it, falling back to the owner(s).
- **Platform admin** (assumption): a flag outside the six roles, limited to `/api/v1/platform/*` (plan catalogue and visibility, organisation provisioning and suspension); it never passes `OrgContextGuard` and has no tenant data access (support access only by owner-granted, time-boxed, audited grant). If the owner rejects it, plan visibility becomes an Owner-level company setting.
- Plan **visibility**, **availability**, **entitlements** (per-organisation snapshot, `@RequireEntitlement`) and **billing** are separate; hiding a plan never revokes entitlements.

## Implementation (Phase 2c)
- **Roles are code.** The six roles and their permission bundles live in `src/permissions/catalogue.ts` (typed keys, so a typo is a compile error). There are no roles or permissions tables in v1; custom per-organisation roles would add them later.
- **One global `AccessGuard`** (after `AuthGuard`) decides: `@Public`, `@Authenticated`, `@PlatformOnly` (flag re-read from the database), or an ACTIVE membership plus the permission (`@RequirePermission`) / any role (`@OrganisationMember`). Non-member, deactivated member and unknown organisation are one 404; a missing permission is a 403 before any record is looked up; an undeclared handler is denied. Roles are read per request, never from the token, so changes apply at once.
- **Beside the permission check** (rbac-matrix.md section 4): only an Owner touches the Owner role; nobody changes themselves; the last Owner is protected, also under concurrency (the active owners are locked before the check).
- **Denials are logged, not stored**: an audit row per 403 would let any member flood the append-only trail.
- **Platform admin** is a flag (`users.is_platform_admin`) set only by `npm run platform-admin` with the owner database credentials (and a security event); it opens `/platform/*` only and never a tenant route. Organisation **suspension** and `@Policy` record rules are deferred (Phase 3 and 5).
- **Organisation creation** is configurable: `ORGANISATIONS_SELF_SERVE` (default off) lets any signed-in user create one and become its Owner; otherwise a platform administrator provisions it and invites the first Owner. Gate G0 decides which model production uses; `GET /meta` tells the UI which one is active.

## Consequences
A simple, auditable model that is less granular than the manual's Auditor and Assessor roles (an auditor-style read-only role would be a seventh role later; per-organisation custom roles stay possible because `role.organisation_id` can be nullable).

## Revisit when
The owner confirms or rejects the platform-admin flag, or customers need per-business-unit scoping or auditor access.
