# fca-backend implementation plan

Work proceeds in controlled phases. **Each phase ends with a report** (functionality, changed files, endpoints and contract version, migrations, tests run and results, known limitations, next task) and, because the Definition of Done spans both repositories, a phase closes only when **fca-backend and fca-frontend both pass `npm run verify`**. The frontend plan mirrors this file in its own repository.

The order below keeps the specification's phase numbers but splits two phases and moves cross-cutting infrastructure earlier ("◆") where later phases depend on it. Features are unchanged.

### Phase 2c — organisations, membership, RBAC ◆ (built)

Decorators `@RequirePermission`, `@OrganisationMember`, `@PlatformOnly` also write `x-access` / `x-permission` into the contract. `@Policy` (record-level rules) is deferred to Phase 5, the first module that needs one. ### Phase 3 — setup modules (built)
**What exists (2026-10-16), backend, contract 0.4.0 (20 operations, see [integration.md](integration.md)):**
- `src/settings`: company information (name, display name, legal name, registration number, sector, **country and DPO email required**, address, DPO name/phone, IANA `timezone`) with optimistic `version`, PATCH semantics (omit = keep, `null` or blank = clear), `company.branding` needed to change the display name; regulator contacts (separate from the DPO; several allowed); logo upload/serve/remove.
- `src/business-units`: name (unique among active units), code (unique per organisation, **archived units keep theirs**), description, head (an ACTIVE member), data sensitivity 1 to 5 (null = not classified, never defaulted), employee count, optional parent (must be active, no cycles, not itself). Units are **archived, never deleted**; archiving a unit that still has active children is refused (`409 BUSINESS_UNIT_HAS_CHILDREN`).
- `src/frameworks`: the catalogue (CDPA, POPIA, GDPR, BDPA, ISO 27701, NIST CSF; **identifiers only, no legal text**) and the organisation's chosen set (`PUT` the full set). Removing a framework keeps its history (the join row gets a `removed_at` time, it is not deleted).
- `src/plans` and `src/organisations/entitlements.*`, `src/organisations/subscription.controller.ts`, `src/platform`: four **placeholder** plans (Starter 5 users, Growth 15, Professional 25, Enterprise unlimited + API; limits are not commercially confirmed), `GET /subscription` (snapshot and usage), platform administrators list plans (including hidden ones), hide or show a plan, assign a plan to an organisation (the plan's limits are copied as a snapshot) and optionally pick a plan when provisioning. **No plan = no limits (never zero).** With a plan, inviting and reactivating are refused when active members plus open invitations would exceed the user limit (`403 USER_LIMIT_REACHED`).
- `src/storage`: `StorageProvider` + local driver (`STORAGE_LOCAL_DIR`, default `.local-storage`, git-ignored). Logos: PNG or JPEG up to 512 KiB, recognised by their bytes (no SVG), served only through an authorised endpoint with `ETag`, `nosniff` and a locked-down CSP. A logo change does **not** bump the organisation `version` (it is a separate resource).
- Migrations `…140000_setup_modules` (checks, partial unique indexes, RLS on the new tenant tables, seeds the six frameworks and four plans, recreates `fca_platform_organisations` with `plan_name`) and `…160000_company_sector_and_unit_fields` (sector; head, sensitivity, employees, parent with composite foreign keys; code unique including archived). The folder names carry hand-set times so that the helper functions of 2c exist first (`prisma migrate dev --create-only` stamps the UTC clock, which sorted before them: rename the folder).
- Seeded demo company for hand testing: `npm run seed:dev` ([neon-setup.md](neon-setup.md) section 7: accounts, password, what it creates).

**Deviations from the original plan (below), on purpose:**
- No `framework_versions` and no `deadline_policies` tables yet: they have no consumer before Phase 4 (versions and content) and Phase 7 (deadline policy). The catalogue holds identifiers only.
- No `@RequireEntitlement` decorator: the only enforced limit (users) is checked directly inside the invite and reactivate transactions. The decorator arrives with the first feature entitlement (Phase 8 and later).
- The subscription **page** is Phase 10 (the endpoint exists; the frontend shows nothing for it yet beyond the platform plan pages).
- "Reassign" is moot until records point at business units (Phase 5 and later); only archive exists. The "linked records block deletion" criterion is met by never deleting.
- The logo is stored and served but the app shell does not display it yet.
- **No new automated tests** (see the status row). The existing suites and the generated tenancy + RBAC matrix cover the new routes' access rules; behaviour rules (limits, cycles, archive, logo checks, field requirements) are **not** covered by a permanent test.

**Original plan for this phase:**
- Endpoints: `GET/PATCH …/settings` (company information, DPO and regulator contacts, `timezone`), logo upload/download, `…/business-units` (CRUD, archive/reassign), `…/frameworks` (applicable frameworks), `GET /frameworks`, `GET /plans`, `…/subscription`, `/platform/plans` (visibility).
- Migrations: organisation settings columns, `business_units`, `frameworks`, `framework_versions`, `organisation_frameworks`, `plans`, `plan_visibility`, `organisation_entitlements`, `deadline_policies` (empty).
- ◆ `StorageProvider` abstraction + local driver (logo) and `@RequireEntitlement`.
- Exit: changing frameworks never deletes history; hiding a plan never revokes entitlements (tests).

### Phase 4 — compliance mapping and content (built; content waits for verification)
**What exists (2026-10-16), backend, contract 0.5.0 (15 operations, see [integration.md](integration.md)):**
- Migration `20261016180000_compliance_mapping`: `framework_versions` (status, licence class, source URL and citation, retrieval time, `source_hash` of the stored source file, `content_hash` of what was reviewed, verifier and time), `requirements` (tree by composite foreign key inside one version: identifier, kind, title, description, `text_source`), `mapping_pack_entries` (default mappings that come from a CITED crosswalk), and the tenant tables `governance_areas` and `organisation_mappings` (RLS on). Hand-written: checks (a verified version needs a named verifier; a seed mapping points at its pack entry; a user mapping needs a rationale), partial unique indexes (area name among active areas; one active mapping per pair; **one copy of a pack entry per organisation in any state**, so Load Default Mappings never duplicates and never resurrects an archived row), and **immutability triggers**: a version beyond DRAFT, its requirements and its pack entries cannot be updated or deleted (only the status may move forward). `prisma/sql/runtime-role.sql` withholds INSERT/UPDATE/DELETE on the three global tables from `fca_app`: only the owner-run loader writes them.
- `src/governance-areas` (the rows of the mapping table; the organisation's OWN labels, none are shipped; archived, never deleted), `src/compliance-mappings` (list, get, create, update, archive/unarchive, the matrix, Load Default Mappings), `src/frameworks` (reference guide with provenance, requirement lists). Permissions are the existing `mapping.view`, `mapping.edit`, `mapping.loadDefaults` (areas use `mapping.*` too; no new keys).
- Rules enforced in the service: a mapping links requirements of two DIFFERENT frameworks that both belong to a loaded, verified version; the same pair cannot be mapped twice among active mappings (either direction); a mapping filed under an area needs an active area; a mapping copied from the pack can only change its area and review status; archived areas that still hold mappings stay visible in the matrix (flagged), so archiving an area never hides a mapping.
- Load Default Mappings: one transaction; applicable frameworks only; `createMany` with `skipDuplicates` (ON CONFLICT DO NOTHING); returns `{ inserted, skipped, failed, frameworks }` (`failed` is empty today because one set-based insert cannot fail per row: a database error rolls everything back); `422 SEED_DATA_UNAVAILABLE` with zero writes when no verified pack exists, `422 NO_FRAMEWORKS_SELECTED` when none is applicable; audited as `mapping.defaults_loaded`.
- **Content tooling** (`scripts/frameworks/`, npm `frameworks:status|extract|verify|load`): `extract` parses a stored primary source into `prisma/seed-data/<framework>/<version>/pack.json` (a DRAFT); `verify -- <pack> --by "Full Name"` is the act of a named person stating they compared the pack with the source; `load` (owner credentials, `DIRECT_URL`) loads only verified packs whose content still matches the verified hash and whose stored source file is unchanged. Extracted so far (drafts): **NIST CSF 2.0** from the official CSF 2.0 Reference Tool export (6 functions, 22 categories, 106 subcategories: the published structure; 91 withdrawn CSF 1.1 entries in the export were excluded mechanically) and the **GDPR** from the English Official Journal text of the EU Publications Office (11 chapters, 99 articles; identifiers and headings only, never the operative text). Both carry source URL, retrieval time and SHA-256 of the stored file; see [frameworks/source-registry.md](frameworks/source-registry.md).
- **No default mappings are shipped**: the plan requires a cited crosswalk or a named legal reviewer and none was supplied, so every pack has `mappings: []` and Load Default Mappings answers 422 until one is. CDPA, POPIA, BDPA and ISO 27701 have no pack (shells), by design.
- **The row's own sheet** (2026-10-21, contract 0.15.0, migration `20261021120000_compliance_mapping_sheet` — authored offline, **applied by the owner**): the sample's Compliance Mapping screen is a sheet the organisation writes itself, so a row now also carries `category` (≤ 80) and `controlObjective` (≤ 2000) on `governance_areas`, plus one free-text reference per framework column in the new tenant table `area_framework_notes` (unique per organisation+area+framework, RLS on, a `CHECK` bounding the text to 1–500 trimmed). Written through the area route (`notes` is the whole desired set; a `frameworkId` outside the active catalogue is `400 UNKNOWN_FRAMEWORK` and writes nothing), read on the matrix row (`areaCategory`, `areaControlObjective`, `notes[]`), and cleared by `DELETE …/governance-areas/{areaId}/mapping-sheet`, which empties the row's own text and touches neither the area nor its verified mappings. **What exists (2026-10-18), backend, contract 0.9.0 (6 new operations over 148 paths, see [integration.md](integration.md)):**
- `src/dashboard` (`DashboardController`, `DashboardService`, `DashboardRepository`, `dashboard.dto.ts`, `dashboard.module.ts`), wired into `src/app.module.ts`, and the pure rules in `src/domain/dashboard/metrics.ts` — availability vocabularies, the eligibility and newest-revision rule, `maturityRoll`, `exposureRoll`, `gapBandsOf`, `topRisks`, the six getting-started steps and their wording. No new Prisma model, **no migration**.
- `GET …/dashboard/summary` (`maturity.overall`, `risk.exposure.overall`, `onboarding.progress`), `GET …/dashboard/frameworks` (`frameworks.coverage` + `maturity.byFramework`), `GET …/dashboard/gap-analysis` (`gap.analysis` per governance area), `GET …/dashboard/top-risks` (`risk.top`), all four gated `dashboard.view`; `POST …/dashboard/ai-assessment` (`ai.run`) answers `503 FEATURE_UNAVAILABLE`; `POST …/reports/executive-dashboard` (`reports.export`) renders the one-page PDF.
- `src/reports/definitions/executive-dashboard.ts` — the template const (`executive_dashboard` v1) and `buildExecutiveDashboard()`, rendered from the four payloads through `DashboardService`, which `DashboardModule` exports. `ReportsService.generateExecutiveDashboard()` stores the record, its `dataSnapshot` and its `report.generated` audit row through the same `store()` path the Phase 5 report uses. `ReportParamsDto.assessmentId` became nullable because this document spans the organisation (the `Report` column already was).
- `GET …/risks` gained `basis`, `likelihood` and `severity` (`src/risks/risks.{dto,service,repository}.ts`): a heat-map cell drills down into the register's own list, reading exactly the factor pair the cell was plotted from. No new route, no recomputed count.
- `ErrorCode.FeatureUnavailable` (`503`) added in `src/common/errors/app.exception.ts`, deliberately distinct from `SERVICE_UNAVAILABLE`: a healthy server refusing a not-yet-built feature must not look like something worth queueing a retry for.
- Every read is **one unit of work** of set-based queries (`cycles`, `items`, `organisationFacts`, `applicableFrameworks`, `frameworkVersions`, `onboardingCounts`, `openTasksByFramework`, `openRisks`, `openTasksForItems`) — no query per card, none per row — and all four payloads return `asOf` with the organisation's `timezone`.
- **No new permission key**, so `docs/rbac-matrix.md`, `test/rbac-matrix-doc.spec.ts` and `test/access-declaration.e2e-spec.ts` pass unchanged; `contracts/openapi.json` and `contracts/CHANGELOG.md` are at 0.9.0.

**The design decision that shapes the phase: the dashboard adds no second copy of a number.**
- Sections whose server already computes them keep their own endpoint and the dashboard calls it: Overall Risk Exposure counts and the 5×5 grid (`GET …/risks/summary`, `GET …/risks/heatmap`), RoPA Monitor (`GET …/ropa/monitor`), Priority Matrix (`GET …/priority-matrix`), DSAR SLA (`GET …/dsar/sla`), Open Breaches (`GET …/breaches/summary`). `docs/metrics/README.md` says the dashboard's cards "are the counts above, not recomputed ones", so re-implementing any of them in a dashboard repository would create a second definition of `overdue` that could disagree with the first. Only metrics with **no** server computation yet get new code.
- New, all gated `dashboard.view` (`src/permissions/catalogue.ts:71`; no permission key is added): `GET …/dashboard/summary` (the organisation-wide maturity roll-up, the exposure mean under the bands in force, the getting-started steps, `asOf` and the per-section availability flags); `GET …/dashboard/frameworks` (one entry per applicable framework carrying `frameworks.coverage`, `maturity.byFramework` and the gap-band split — the same payload feeds the bar/radar/table comparison and the compliance cards); `GET …/dashboard/gap-analysis` (`gap.analysis` per governance area, sorted by gap then exposure, with the highlight threshold in the body); `GET …/dashboard/top-risks` (`risk.top`, default 10, `basis=residual|inherent`).
- Heatmap drill-down is new filters on the existing list, not a new endpoint: `GET …/risks?basis=&likelihood=&severity=`, read against the same factor pair the cell was plotted from, with the Phase 6 `includeClosed=false` to match what the grid plots (a CLOSED risk is history, not exposure). The drill-down must land on the same register page the sidebar already opens.
- `POST …/reports/executive-dashboard` (`reports.export`) renders the one-page PDF; `POST …/dashboard/ai-assessment` (`ai.run`) answers `503 FEATURE_UNAVAILABLE` until Phase 10 builds `src/ai`.
- **The organisation-wide rule** (`maturity.overall`, `frameworks.coverage`, `gap.analysis`): an item counts when its cycle is `IN_REVIEW` or `APPROVED` (a draft is nobody's finding; a superseded cycle is an older revision of the same work), and per subject only the newest revision counts — subject = `requirementId`, else `governanceAreaId` with the business unit, else the item itself; newest = latest sign-off instant (`approvedAt` then `submittedAt`, then `createdAt`, id last). Everything is then rolled up by `summarise()` from `src/domain/scoring/scoring.ts` — the same function the per-assessment summary uses — so a mean, a coverage pair and a `notRated` count cannot mean two things.
- **Methodologies are never averaged together**: the eligible set carries each cycle's `methodologyId`/`methodologyVersion`; one pair ⇒ the exposure mean and its band (`bandFor` over `scoring.bandsInForce(tx)`, the bands in force *today*, since the org-wide mean is not a per-cycle score); more than one pair ⇒ `availability: unable_to_calculate` listing the pairs. Maturity and gap are levels, not exposure scores, and stay measurable.
- Every endpoint is ONE unit of work with a handful of set-based reads (`findMany` with a narrow `select`, `groupBy`-shaped aggregation done in `src/domain/dashboard/`), never a query per card or per row. `risk.top`'s related task comes from one read of the open tasks, joined in memory.
- **No new Prisma model, so no Phase 8 migration.** Everything the dashboard shows is already stored; a denormalised counter table would be a second truth.
- Golden tests stay out of scope (owner decision, carried from Phases 3–7): the definitions live in `src/domain/dashboard/metrics.ts`, pure and untested by new specs; Phase 11 writes the golden fixtures.

**Original plan for this phase:**
- Endpoints: `GET …/dashboard/summary` (sections with availability/status/coverage), lazy endpoints for heatmap (+ drill-down), comparison (bar/radar/table), gap analysis, RoPA monitor, priority quadrants, top high-risk areas; `POST …/dashboard/ai-assessment` placeholder gated until Phase 10.
- Exit: every metric has a definition sheet entry and golden tests (empty, partial, full); dashboard uses set-based queries, not per-card fan-out.

**The second exit criterion is met in full** (one unit of work of set-based reads per endpoint, and the drill-down reuses the register's own query) **and the first partly**: every metric now has a *finalised* definition sheet entry — [metrics/README.md](metrics/README.md) "What Phase 8 built (contract 0.9.0)" rewrites the seven `/8` rows and the `risk.top` row against what the code actually decides — while the golden fixtures are the owner-deferred part (Phase 11).

**Deviations from the original plan (below), on purpose:**
- **No "lazy" dashboard endpoints for the heat map, the RoPA monitor or the priority quadrants.** The plan listed them as dashboard routes; the phase's own rule (no second copy of a number) means the screen calls `GET …/risks/heatmap`, `GET …/ropa/monitor` and `GET …/priority-matrix` instead, and a `dashboard/*` version of each would be a second implementation of the same count. The heat map needed one thing only: a way to ask the register for the risks in one cell, which became filters on `GET …/risks`.
- **The priority quadrants card needs no new code.** `GET …/priority-matrix` is already organisation-scoped (Phase 5): it counts every item the tenant has, derives each quadrant from the saved answers under ruleset v1, reports an incomplete questionnaire as `unclassified` rather than dropping it, and says `partial` when its scan hit the ceiling. A dashboard roll-up of it would merge two questionnaires into one priority nobody chose, and could disagree with the matrix page.
- **The Executive Dashboard PDF covers the four dashboard payloads only** (summary, frameworks, gap analysis, top risks) plus the getting-started steps. The incident and register cards (DSAR SLA, open breaches, RoPA monitor, priority matrix) stay live on the screen and belong to the Consolidated DPO Report (Phase 9a), which is the document whose audience is the regulator; scoping it this way avoids exporting five modules' services from their own modules and keeps the two documents doing different jobs.
- **`FEATURE_UNAVAILABLE` is a new error code**, not `SERVICE_UNAVAILABLE`: the AI placeholder must be distinguishable from a real outage, because a client queues a retry for one and must not for the other. It is documented in the contract as the 503 of `POST …/dashboard/ai-assessment`.
- **The drill-down filter is `basis` + `likelihood` + `severity`, not `excludeClosed`**: `includeClosed` already existed on `GET …/risks` since Phase 6, so the grid's "not CLOSED" is expressed with the parameter the register already has.
- **`maturity.overall`'s `not_configured` case moved to `frameworks.coverage`.** The sheet said "no frameworks ⇒ `not_configured`" for the maturity figure; on the server, a lack of applicable frameworks is a fact about the framework list, and `GET …/dashboard/frameworks` is the endpoint that can say it with a `message`. The maturity metric therefore answers `ok` or `not_assessed` only, so no client has to guess which kind of nothing it is looking at.
- **`limit` on `risk.top` is capped at 25** (default 10): the list is a dashboard section, not an export path, and a register that needs more rows has `GET …/risks` with its own filters.
- **No new automated tests** (owner decision, carried from Phases 3–7). The rules were exercised with throwaway in-process reads against the seeded demo organisation and deleted afterwards; the existing suites still cover the new routes' access declaration, layering and contract version. Adding the golden fixtures is Phase 11 work.

### Phase 9 — reports, audit, training, manual
- 9a: report catalogue + history, remaining templates, audit trail search/export. 9b: training (courses, lessons, quiz grading **server-side**, enrolments, assignments, certificates). 9c: user manual (frontend-bundled content; no backend beyond optional search index).
- **9a backend, as built** (contract 0.11.0): `definitions/registry.ts` is the catalogue — one `ReportTemplateDefinition` per template (`id`, `version`, `title`, `description`, `generate`, `params`) plus the planned list, and the same file supplies `REPORT_PERMISSIONS` that the controller decorators require, so what the API advertises and what it enforces cannot drift. History (`GET …/reports`, cursor, newest first, filtered by template/status/cycle/UTC-day window) and `GET …/audit` + `GET …/audit/export` (5,000 events per file, `422 EXPORT_RANGE_TOO_LARGE` beyond, `changes` cut at 1,000 characters, the export itself audited) came with it.
- **9a deviations from the one-line scope.** (1) *Async is declared per template, not applied to all of them*: the two single-payload documents still render in the request and answer `201 READY`, because a Phase 5/8 behaviour change would be a regression the plan does not ask for; only the DPO pack, which spans seven registers, goes through `report.generate` and `202`. (2) *The remaining templates are the DPO pack and nothing else* — Compliance Status, RoPA and Maturity & Gap are covered by the dashboard/assessment/DPO documents rather than rebuilt, and Training Certificate (9b) and AI Risk Assessment (10) are listed as `planned`. (3) *The trail exposes ids, never names*: `audit.view` reaches a Compliance Manager while `users.view` does not, so an audit row cannot carry a member's name or address; the same asymmetry is why the DPO pack prints no data-subject contact details. (4) *Reads are bounded and say so* (100 rows per page, a scan cap, 60 printed rows per section, `notPrinted` named in the document) instead of one unbounded query per section. (5) *No scheduler is configured* (owner decision), so an async report stays `PENDING` on a function host until the internal tick runs — the history list shows that state truthfully rather than the UI pretending otherwise. (6) **No new automated tests** (owner decision, carried from Phases 3–8); the new routes are covered by the existing access-declaration, layering and contract-version suites, and the DPO renderer was exercised with throwaway document builds — every register empty and every table filled from rows derived from the contract's own DTO schemas, plus the "the register holds more than this document reads" state — which found and fixed one real defect (an unassessed organisation printed "Current maturity Not assessed of 5"), all deleted afterwards.
