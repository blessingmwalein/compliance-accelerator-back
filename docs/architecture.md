# fca-backend architecture

Status: **Phase 0 foundation implemented; everything else specified here is the target** (sections marked *Phase N* are built in that phase). Decisions are recorded in [docs/adr](adr/); rules for working in each area are in `.claude/skills/`.

## 1. Scope and pins
Multi-tenant REST API for the FCA GRC platform. Node 24, TypeScript 6.0.3, NestJS 12.1 (ESM), Prisma 7.10 + `@prisma/adapter-pg`, PostgreSQL on Neon, Vitest 4.1, oxlint. Exact pins and spike results: [ADR-0001](adr/0001-toolchain-pins.md). The frontend is a separate repository; the contract between them is [contracts/openapi.json](../contracts/openapi.json) ([ADR-0002](adr/0002-repo-and-contract-strategy.md)).

Each feature module follows one template: `<x>.controller.ts`, `<x>.service.ts`, `<x>.repository.ts`, `dto/*.dto.ts`, `<x>.policy.ts` (record rules), `<x>.module.ts`, specs.

## 3. Layering rules
`controller → service → repository → PrismaService`, plus `service → domain`. Controllers do HTTP only; services own rules, transactions and audit; **only repositories import `PrismaService`** (health probes excepted); `domain/` has no framework imports. Cross-module calls go service to service. An architecture test (added with the first real module) enforces the import rules. See `backend-architecture`.

## 4. Request pipeline (order is part of the contract)
1. `pino-http` assigns/propagates `X-Request-Id` (inbound ids are accepted only if they match `^[A-Za-z0-9._-]{8,64}$`) and redacts `authorization`, `cookie`, `set-cookie` in logs. **[done]**
2. `helmet`, then exact-origin CORS with credentials (`CORS_ORIGINS`), exposing `X-Request-Id`. **[done]** (Swagger is mounted before helmet so its UI works; docs are off by default in production.)
3. `@nestjs/throttler` coarse per-IP limit (`THROTTLE_LIMIT`, stricter `@Throttle` on the auth routes), registered **before** the auth guard so a flood is cut before any database work. **[done, 2b]**
4. Body parsing (malformed JSON becomes a 400 problem).
5. `AuthGuard`, **deny by default** (`@Public()` opts out, `@Authenticated()` = any signed-in user): verifies the access JWT, then re-reads the session from the database on every request. **[done, 2b]**
6. `AccessGuard` (global, right after `AuthGuard`; **built in 2c**) resolves the caller's ACTIVE membership of `:organisationId` through a SECURITY DEFINER lookup (404 for a non-member, a deactivated member and an unknown organisation alike), checks the role against the permission catalogue (403 before anything is looked up) and only then writes organisation, membership and role to the request scope (`RequestContext.update`). `@PlatformOnly` routes check the platform-admin flag instead; a handler with no declaration is denied. `test/organisations/access-matrix.int-spec.ts` proves the order and the outcomes for every organisation route.
7. Entitlements (`@RequireEntitlement`) arrive with the plan tables in Phase 3.
8. Global `ValidationPipe` (whitelist, forbid unknown, transform). **[done]**
9. Handler → service → repository.
10. Serialisation interceptors; `ProblemDetailsFilter` renders **every** error as `application/problem+json`. **[done]**

## 5. Tenancy (see [ADR-0004](adr/0004-tenancy-and-rls.md), `database-and-tenancy`)
Routes `/api/v1/organisations/:organisationId/…`; `AccessGuard` (**built**, 2c) → `RequestContext` (AsyncLocalStorage, **built**) → tenant-scoped repositories extending `TenantRepository` (no bare-id methods, **built**) → Prisma `$extends` safety net `assertTenantScoped` (asserts `organisationId` on every tenant-model query and fails closed, **built**) → composite foreign keys (rule enforced by the catalogue test, **built**; no tenant-to-tenant relation exists yet) → **row-level security** (**built and ON since 2c**, migration `row_level_security`: every tenant table has a `tenant_isolation` policy on `app.org_id`, set by `UnitOfWork` as the first statement of each transaction, transaction-local so safe behind PgBouncer; fails closed; the few reads that happen before a tenant is known use SECURITY DEFINER functions; `test/database/rls.int-spec.ts`). Foreign or unknown records are 404. `test/database/catalogue.spec.ts` parses `prisma/schema.prisma` and fails the build if a table is neither tenant-owned (`TENANT_MODELS`), global (`GLOBAL_TABLES`, with a reason) nor the root; `test/architecture.spec.ts` confines Prisma and raw SQL to repositories and infrastructure. Both are proven to fail on planted violations.

## 6. Data conventions
UUID primary keys (v7 if supported); `timestamptz` instants; `date` business dates; `snake_case` columns; `version` integer for optimistic concurrency; soft delete only where legally or audit-relevant; per-organisation unique keys; every tenant table indexed on `organisation_id` first; **raw inputs stored, derived values computed** (snapshots carry methodology and band versions); unassessed is `NULL`. Cursor pagination (`limit` default 25, max 100), allow-listed sort and filter fields, `Idempotency-Key` on creates.

## 7. Authentication and authorisation (see ADR-0003, ADR-0005, `security-and-rbac`) *[authentication built in 2b; roles, permissions, organisations, members and invitations built in 2c]*
**Built (2b):** `POST /auth/register|resend-verification|verify-email|login|refresh|logout|forgot-password|reset-password` and `GET /me` (contract 0.2.0). 15-minute HS256 access JWT with only `sub` and `sid`; opaque 32-byte refresh token in an HttpOnly `SameSite=Lax` cookie scoped to `/api/v1/auth`, stored as SHA-256, **rotated on every use**; presenting a used token again revokes the whole session unless it happens within a 10-second grace window (several tabs restoring at once). Sessions have an absolute 30-day lifetime. argon2id (`@node-rs/argon2`). Verification and reset tokens are random 32 bytes, stored hashed, single use, 24 h / 30 min, created by the email job at send time and delivered in the **URL fragment**; consumed by POST. Login lockout is Postgres-backed (5 failures per account or 30 per IP in 15 minutes, then 30 s doubling to 15 min, `Retry-After`) and keyed on **keyed hashes** of the address and IP, so unknown addresses lock exactly like real ones. Registration, resend and forgot-password answer 202 whatever the account state; a wrong password and an unknown address are the same 401 and both pay for an argon2 verification. A password reset ends every session. Cookie endpoints also need `X-Requested-With: fca-web` and an allowed Origin. Every outcome that matters writes a `security_events` row.

**Built (2c):** the typed permission catalogue and six role bundles (`src/permissions/catalogue.ts`, checked against [rbac-matrix.md](rbac-matrix.md) by a test), the global `AccessGuard`, `GET /organisations`, `POST /organisations` (self-serve, off by default), `GET /organisations/:id/me` (role + permissions), members (list, change role, deactivate, reactivate), invitations (create, list, resend, revoke, inspect, accept; the email job creates the one-time token at send time), platform provisioning (`/platform/organisations`, platform-admin flag granted only by `npm run platform-admin`), cursor pagination, optimistic locking (`version`), the last-owner rule under concurrency, and RLS.

**Still to come:** MFA (reserved), entitlements and plan visibility (3), organisation suspension. Record-level `@Policy` rules were planned "with the first module that needs one, Phase 5" and were **not needed**: the one candidate (remediation, where only the assignee or an editor may act) is enforced in the service against the loaded record (`403 NOT_ASSIGNEE`) with the handler still carrying exactly one access decorator. Principles: Six fixed roles (Company Owner, Company Admin, Compliance Manager, Course Administrator, Standard User, Read Only) as bundles of `module.action` permissions ([rbac-matrix.md](rbac-matrix.md)); DPO is a designated contact, not a role; a platform-admin flag (assumption) is confined to `/platform/*`.

## 8. Audit *[write side built in Phase 2a, read side built in Phase 9a, UI Phase 9a]*
Implemented: `UnitOfWork.run(tx => …)` + `AuditService.record(tx, { action, entityType, entityId?, entityLabel?, outcome?, changes? })`. Actor and request id come from `RequestContext`, the organisation from the verified tenant, the time from the database; `changes` goes through `redactChanges` (secrets only: callers still pass field-level before/after values, never DSAR or breach free text). The migration adds a trigger that rejects UPDATE and DELETE for every role; `prisma/sql/runtime-role.sql` also withholds the privileges from the runtime role. `audit_events.organisation_id` is mandatory, so events that belong to no organisation (login attempts, platform actions) need a separate global `security_events` table, planned for Phase 2b. Deleting an organisation that has audit events is blocked (`ON DELETE RESTRICT`): tenant offboarding is an open concern to design before production.

Phase 9a added the **read** side: `GET …/audit` (`audit.view`) is a cursor page, newest first, filtered by period (`from`/`to` as whole UTC days), actor (`actorUserId`), action, outcome, entity type and entity id, and `GET …/audit/export` (`audit.export`) answers the same filters as CSV with `Content-Disposition: attachment`; the export writes an audit row of its own, because "who read the trail" belongs in the trail. A row exposes the actor only as `actorUserId` — `audit.view` reaches a Compliance Manager while `users.view` does not, so the trail cannot hand out member data the caller could not otherwise read. `changes` is deliberately not full-text searchable: searching JSON would be a sequential scan over an append-only table, and the filters an auditor actually asks with are the indexed columns. There is no write, edit or delete route for anyone.

`audit_events` (tenant scoped, append-only): `occurred_at` (server clock), actor, action (typed catalogue), entity type/id/name, `changes` (JSONB, sensitive fields redacted), request id, outcome. Written **inside the same transaction** as the change and **fail-closed**. Immutability is enforced in the database (`REVOKE UPDATE, DELETE` for the app role + trigger) so ordinary users and the app role cannot alter history. The legacy client-side, swallowed, client-timestamped audit log is the anti-pattern.

## 9. Error contract (**implemented**)
RFC 9457 `application/problem+json`: `{ type: "urn:fca:problem:<code>", title, status, detail?, code, errors?: [{ path, code, message? }], requestId }`. Stable codes live in `ErrorCode` (`VALIDATION_FAILED`, `NOT_FOUND`, `FORBIDDEN`, `CONFLICT`, `DATABASE_UNAVAILABLE`, …). Unexpected errors return a generic 500 and are logged with the request id; internals never leak. Documented per endpoint via `@ApiProblemResponse`.

## 10. Scoring and metrics (see `grc-domain`, [metrics](metrics/README.md)) *[scoring built in Phase 5, registers in Phase 6, incidents in Phase 7, dashboard metrics in Phase 8]*
Pure `src/domain/scoring`: versioned `Methodology` (`exposure_v1`, `risk_matrix_v1`, `maturity_v1`), `exposure/gap/bandFor/rollUp`, unassessed = `null`, aggregates return coverage. Metric states are `availability` × `status`. **Two arithmetic systems, deliberately apart:** `exposure_v1` (sensitivity × severity × likelihood, 1–125) rates an assessment item and an organisation may customise its bands through `GET …/scoring`; `risk_matrix_v1` (likelihood × severity, 1–25) rates a register risk and Phase 6 applies the **reference bands to every organisation** (`src/domain/risk/policy.ts`, frozen in the row through `methodologyId`/`methodologyVersion`). A client sends factors and never a score; the database CHECK refuses a row whose factors, score and band disagree. `src/domain/registers/` adds the second shared piece of pure logic: one review model (`not_reviewed | overdue | due_soon | ok`, the 30-day reference lead, today in the organisation's zone) used by all five registers, and the vocabularies (statuses, the six Article 6 bases, the retention triggers, the disposal targets) with their transition tables. `src/domain/incidents/` is the third shared piece: calendar-day deadline arithmetic against the policy row a record froze, the one `DeadlineState` vocabulary (`ok | due_soon | overdue | not_configured`) that `DeadlineViewDto` renders in three places, the DSAR / breach / evidence-review / reminder transition and extension tables, and the seven alert kinds with their dedupe keys and skip reasons. Phase 7 keeps the register rule that **a date is judged in the organisation's zone** — `todayIn`, `utcDay` and `alertInstantOn` are the only ways a due day becomes a verdict or an email a moment, so a deadline is never announced as passed while it still has hours to run. Each module ships its metric definition and golden tests from Phase 5 — the **definitions** ship (see [metrics/README.md](metrics/README.md), "What Phase 5 built", "What Phase 6 built", "What Phase 7 built" and "What Phase 8 built"); the golden tests were dropped by the owner's no-new-tests decision and are Phase 11 work. The dashboard (Phase 8) composes them: `src/domain/dashboard/metrics.ts` holds the organisation-wide rules that no other module owns — which cycles count as the organisation's finding (only `IN_REVIEW`/`APPROVED`), one subject = one current answer (the newest signed revision per requirement, area-and-unit, or ad-hoc item), the maturity/exposure/gap roll-ups built on the same `summarise()` and `bandFor()` the per-assessment summary uses, the refusal to average two methodologies (`unable_to_calculate`), the top-risk ordering and the six getting-started steps. Four endpoints (`…/dashboard/{summary,frameworks,gap-analysis,top-risks}`, all `dashboard.view`) each answer in ONE unit of work of set-based reads and carry their own `availability`/`status`, so an absent figure is explained rather than shown as zero and one section failing never blanks the page. Sections another module already computes keep their own endpoint and the screen calls those — the heat map, the RoPA monitor, the priority matrix, the DSAR SLA and the breach summary are **not** re-derived here, which is what keeps one word (`overdue`) meaning one thing; the heat map's drill-down therefore became three filters on `GET …/risks` (`basis`, `likelihood`, `severity`) rather than a dashboard copy of the grid.

## 11. Jobs, email, notifications (ADR-0006, `notifications-and-jobs`) *[outbox and email built in 2b, deadline alerts built in Phase 7]*
**Built (2b):** `jobs` table, `JobsService.enqueue(job, tx)` (deterministic `dedupeKey`, `ON CONFLICT DO NOTHING`), `JobRunner.runBatch` (claim with `FOR UPDATE SKIP LOCKED`, lease, exponential backoff with jitter, dead letters, lease-expiry reclaim and dead-lettering on the last attempt, per-job failure isolation, tenant jobs run inside their organisation scope), handlers found by `@JobHandler(type)` scanning, `POST /internal/jobs/tick` (HMAC-SHA256 over `timestamp.POST.path`, 5-minute window, 404 when no secret, excluded from OpenAPI) and an in-process poller (`JOBS_RUNNER=inproc`, backs off when the database is down). Email: `EmailProvider`, `FileMailTransport` (writes `.eml` to `DEV_MAIL_DIR`, nothing is delivered), link-only templates with escaping and an http(s)-only link check, one `email_deliveries` row per attempt keyed on the address.

**Built (Phase 7):** the first deadline-driven alerts, and **no `scheduled_jobs` table was needed** — the plan deferred recurring definitions to this phase, and the design turned out not to want one. A record queues its own outbox job **inside the transaction that writes it**, with `runAt` = 08:00 **in the organisation's zone on the day it names** (`alertInstantOn`), so a due-soon warning and an overdue warning are two queued rows with two instants rather than a nightly sweep that recomputes them. The dedupe key `<kind>:<recordId>:<deadlineDay>` makes a retried job land on the same `alert_deliveries` row and an unchanged deadline write nothing; the row is created `QUEUED`, only its outcome changes (a database trigger refuses any other update and any delete), and a skip is a visible row with one of `NO_RECIPIENT`, `PREFERENCE_OFF`, `STALE_DEADLINE`, `ALREADY_HANDLED` — not an absence. Handlers are at-least-once, so each one re-reads the record and re-checks the deadline, the preference and the terminal status before it sends. `scheduled_jobs` (recurring definitions) stays deferred until something genuinely recurring exists; SMTP/ESP waits for gate G0.

Design: outbox + lease runner (`FOR UPDATE SKIP LOCKED`), in-process poller or HMAC-signed `POST /internal/jobs/tick`, idempotent handlers with deterministic dedupe keys, `EmailProvider` (file transport in dev), `email_deliveries` keyed on address, in-app `notifications`.

## 12. Storage and evidence (ADR-0007) *[core built in Phase 5, repository built in Phase 7]*
**Built:** `StorageProvider` with two drivers — the local disk (`STORAGE_LOCAL_DIR`, dev only; `validateEnv` refuses `local` in production) and **S3-compatible object storage** (`STORAGE_DRIVER=s3`: Supabase Storage speaks the protocol, so do R2, B2, Wasabi and AWS S3) behind one contract, so where the bytes live is configuration and not code (ADR-0007). Opaque per-organisation keys, proxied downloads only (bearer-authorised, `Content-Disposition: attachment`, `ETag` = the checksum), magic-byte validation, SHA-256, evidence rows linked to assessment items and remediation tasks, upload/rename/link/unlink/download audited.
 Since Phase 6 an evidence row can also be under a legal hold: `fca_hold_covers('EVIDENCE', …)` refuses its deletion in the database, and a hold that covers a whole rule reaches every record that points at it. Since Phase 7 it is a **repository**: one row now carries many immutable versions (version 1 is stored under `org/<organisationId>/evidence/<id>/1`, where the record id itself is a fresh uuid; a later version adds a second fresh uuid — `…/<number>/<uuid>` — because that number is guessed before the write, and two concurrent uploads that read the same head would otherwise share a key and the loser's rollback compensation would delete the winner's bytes), `currentVersion` names the one a plain download serves, `?version=n` names any other, every read is audited with the version it fetched, and a new version resets the review to `UNREVIEWED` and the scan to `NOT_SCANNED` in the same transaction, because neither a verdict from other bytes nor another version's clean scan can carry over. A review is a decision (`governance.approve` for an outcome, `governance.edit` to reopen, a note required to reject); a scan state is **attested by a person** (`NOT_SCANNED` cannot be attested, `INFECTED` / `UNABLE_TO_SCAN` need a note) and is dated on the attester's own calendar day, not in UTC. Bytes are written before the row and, if the transaction fails, deleted again — a row can therefore never name a file that was not stored, and the only residue an abandoned upload can leave is an object no row points at, which is unlistable and unservable. **Still not built:** `VirusScanner` (hence attestation, not automation), and any scheduled or automatic disposal — the Phase 6 disposal log is a person recording that a disposal happened, nothing deletes on a timer, and no API route deletes an evidence row or a superseded version.

## 13. Reports (ADR-0008, `reports-and-documents`) *[core built in Phase 5, catalogue and async generation built in Phase 9a]*
**Built:** server-side pdfmake rendering of three templates — the Governance Assessment (one cycle, Phase 5), the Executive Dashboard (the whole organisation, Phase 8, drawn from the four dashboard payloads through `DashboardService`) and the **Consolidated DPO Report** (Phase 9a) — with an SVG bar chart from the same DTO the screen reads, a `reports` record with its parameter snapshot and data snapshot, size and checksum, and an authorised download with the same header discipline as evidence.

Phase 9a made the catalogue data instead of prose: `src/reports/definitions/registry.ts` holds every `ReportTemplateDefinition` (`id`, `version`, `title`, `description`, `generate`, `params`) and is the only source for both `GET …/reports/catalogue` and the permission keys in the controller decorators (`REPORT_PERMISSIONS`), so what the API advertises and what it enforces are one constant. Planned templates (`training_certificate` 9b, `ai_risk_assessment` Phase 10) are listed beside the live ones so a screen can say "coming" truthfully. `GET …/reports` is the history: cursor pages, newest first, filtered by template, status, cycle and a UTC-day period.

Generation is now declared, not assumed. The two single-payload documents stay **synchronous** (`201` with a `READY` record) because one request can honestly carry their data. The DPO pack is **asynchronous**: `POST …/reports/consolidated-dpo` writes a `PENDING` record and enqueues `report.generate` in the same transaction and answers `202`; the handler reads the eight registers through the services the screens call (`RopaModule`, `RisksModule`, `LawfulBasisModule`, `DsarModule`, `BreachesModule`, `RetentionModule` export their service for exactly this reason), renders, stores through the `StorageProvider`, and writes `READY` with the key, checksum, size, snapshot and `finished_at` — guarded on `status = 'PENDING'`, so a second runner cannot rewrite a finished record, and the orphan bytes are deleted when that guard fails. Only the last attempt records `FAILED`, with `error_code` and a sanitised `error_detail`; a non-`READY` report cannot be downloaded (`409`, and the message says which). `GET …/reports/{id}` is the poll. Generation, readiness, failure and every download are audited (`report.requested`, `report.ready`, `report.failed`, `report.downloaded`).

The DPO document is cover, contents and seven sections (governance, RoPA, risks, lawful basis, DSARs, breaches, retention) with the period presets `last_30_days` / `last_6_months` / `this_year` / `all`, an inclusion rule printed inside it (a record counts if it was open during the window, not only if one date falls in it), a `CONFIDENTIAL — DPO Report` marking option, bounded reads (100 rows per page, a scan cap, at most 60 printed rows per section) and the number of rows that did not fit stated in the document. It prints no data-subject names or contact details, and says why. **Not built:** nothing else in the report surface — PDF preview in the browser and Training Certificate are 9b, the AI-written section is Phase 10, and on a function host the queue is only drained when something calls the internal tick (no scheduler is configured in this build).
