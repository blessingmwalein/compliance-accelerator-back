# Contract changelog

The HTTP contract is `contracts/openapi.json` (`info.version` = `CONTRACT_VERSION` in
`src/meta/contract-version.ts`). Additive change => minor, breaking change => major, docs-only => patch.
Record every bump here in the same commit that regenerates the document (`npm run openapi:export`).
The frontend pins a contract version in its own repository (`contract/CONTRACT_VERSION`).

## 0.14.0 - The three dashboard watch sections are stated by the server rather than drawn from guesses (additive)

The dashboard screen of the sample product leads with a RoPA bar chart and a review list, names items inside each priority quadrant, and plots maturity per governance area per framework. The endpoints behind those three sections answered counts only, so a client could have drawn them in exactly one honest way: by inventing the missing rows. This bump gives each section its data instead. **No migration** — every field below is rolled from columns that already exist. The path count stays 157 and no operation is added; 3 existing operations **gained required fields** and 4 new schemas join the document (`RopaUnitCountDto`, `RopaReviewItemDto`, `PriorityQuadrantItemDto`, `FrameworkAreaMaturityDto`).

| Method | Path | operationId | Access | Notes |
|---|---|---|---|---|
| — | `GET …/ropa/monitor` | `getRopaMonitor` | `data.view` | `byBusinessUnit` (`{ businessUnitId, businessUnitName, activities }`, largest group first, the `null` unit being the unassigned one), `needsReview` (`{ id, name, businessUnitId, businessUnitName, lastReviewDate, nextReviewDate, reviewState, daysRemaining }`, most overdue first), `needsReviewLimit`, `needsReviewTruncated` |
| — | `GET …/priority-matrix` | `getPriorityMatrix` | `governance.view` | each quadrant gains `sampleItems` (`{ assessmentItemId, subject }`, at most 3) and `sampleItemsLimit`. `subject` is the same one line the item list shows |
| — | `GET …/dashboard/frameworks` | `getDashboardFrameworks` | `dashboard.view` | each framework gains `byArea`: this framework's subjects rolled per governance area — `{ areaId, areaName, inScope, rated, current, target, gap, availability }`, biggest mean gap first |

Behaviour that is not visible in the schema:

- **A list the server orders is a list that reads the same on every screen.** `needsReview` is sorted by `daysRemaining` then id and cut at 50 rows; `byBusinessUnit` is sorted by count with first-seen order breaking a tie; `byArea` keeps the same order the gap-analysis rows already use. A client that sorts again, or sorts differently, is the disagreement this avoids.
- **`needsReview` is a display window, never a re-count.** `total`, `overdue`, `dueSoon`, `onTrack` and `notReviewed` still cover every live activity, and `needsReviewTruncated` is the only signal that more rows exist than the list carries. The states that need attention always have a due date, so `nextReviewDate` and `daysRemaining` are non-null here while the same fields stay nullable on an activity row.
- **`sampleItems` names the count, it does not replace it.** The three items are the oldest the scan reaches (ids are UUIDv7), taken from the same single scan the counts come from and read back through one batched item query, so a matrix with ten thousand items still costs one pass. `count` remains the whole truth and `count - sampleItems.length` is the "+N more" a card prints.
- **`byArea` is the framework total, split.** Each row is `maturityRoll` over that framework's own subjects under one area, so the radar's points, the table's cells and the framework's own bar are four views of one roll rather than three computations of it. A subject with no governance area is not dropped and not guessed at: it appears once, named `Not filed under a governance area`.
- **No area name is ever matched against a title.** The sample derives its per-area framework scores by testing whether an area name appears as a substring of an assessment title, which invents a link the data does not hold and silently reports zero for an area nobody named. Every number in this payload comes from a relation the row already carries.

## 0.13.0 - The classification register grades a category at a tier and states its exposure (additive)

The Data Classification page of the sample product shows a category, the tier it is graded at, how exposed it is, how long it is kept, who owns it and whether it is encrypted. The API held a level's name, rank, guidance, owner and review dates and nothing else, so four of those seven columns had no source. 156 paths become 157 (1 new operation, 4 new schemas), and `ClassificationLevelDto` **gained four required fields** (`tier`, `posture`, `retentionPeriod`, `encryptionRequired`) — a client reading a level now always gets all four, and `null` is the answer that means nobody said.

**These fields need migration `20261020120000_classification_tier_and_posture`** (the `ClassificationTier` and `DataPosture` enum types, the four columns on `classification_levels`, and the table's stored `CHECK` re-created with the `retention_period` bound), which is not applied until the owner applies it. Until then every classification route — the list included — fails, because the columns it selects do not exist yet.

| Method | Path | operationId | Access | Notes |
|---|---|---|---|---|
| GET | `…/classification-levels/summary` | `getClassificationSummary` | `data.view` | `{ availability, asOf, total, restricted, confidential, highExposure }` counted over **every live level**, because the page is a cursor page of a scheme that may be longer. `availability` is `no_scheme` when the organisation has no levels at all — an absent scheme is not a scheme of zeroes |
| — | `GET …/classification-levels?tier=` | `listClassificationLevels` | `data.view` | one more filter, taking a `ClassificationTier`; it composes with `q` and `includeArchived`. Levels with no tier match no tier |
| — | `ClassificationLevelDto` | — | — | `tier: ClassificationTier \| null` (`PUBLIC` \| `INTERNAL` \| `CONFIDENTIAL` \| `RESTRICTED`), `posture: DataPosture \| null` (`LOW` \| `MEDIUM` \| `HIGH` \| `CRITICAL`), `retentionPeriod: string \| null` (in words; the rule itself stays in the retention register), `encryptionRequired: boolean` |
| — | `CreateClassificationLevelDto` · `UpdateClassificationLevelDto` | — | — | the same four, all optional. On a PATCH an absent field leaves the tag alone and a `null` clears it, so "we never said" stays sayable |

Behaviour that is not visible in the schema:

- **A tier is a tag beside the scheme, not a replacement for it.** `name` is still the organisation's own word for the level and `rank` still orders it, so a scheme of five levels is a scheme of five levels and one of them can be called "Amber" while tagged `CONFIDENTIAL`. Nothing is seeded: an organisation that has not tagged anything reads back `tier: null` everywhere, and the page shows untagged rather than guessing from the name.
- **The three counts are not a partition of `total`.** `restricted` and `confidential` count tags, `highExposure` counts a stated posture of `HIGH` or `CRITICAL`, and one level can be in none of them, one of them, or two. They are the four cards the reference app shows and nothing more, which is why they are not presented as a breakdown.
- **`posture` is never derived from `tier`, and `encryptionRequired` is a claim, not a check.** A `RESTRICTED` level with no posture has no posture; a level that says encryption is required has said so, and the platform has not verified that anyone does. Both are stated by a person and audited as stated.
- **No report template came with this.** The sample's classification page has no Export PDF button, and the scheme already prints inside the Consolidated DPO Report; a document nobody asked for is not a reason to add one.

The register page of the sample product answers three questions the API could not: which lawful basis justifies this activity, how many activities are traceable to a basis or a data classification, and what the register looks like as a document. **No migration** — `lawful_basis_record.processing_activity_id` has existed since Phase 6, and an activity's bases were already readable from the lawful-basis register; what was missing was the other direction. 153 paths become 156 (3 new operations, 2 new schemas, one enum widened), and three existing schemas **gained required or optional fields**: `RopaActivityDto` now always carries `lawfulBasisRecords` (an empty array means none has been stated), `RopaMonitorDto` gains `linkedToLawfulBasis`, `linkedToClassification` and `unlinked`, and `CreateRopaActivityDto` gains the optional `lawfulBasis`.

|---|---|---|---|---|

Answers the whole `RopaActivityDetailDto`, with the new link in it |

| — | `AuditAction` | — | — | two more values: `ropa_activity.lawful_basis_linked`, `ropa_activity.lawful_basis_unlinked` |

Behaviour that is not visible in the schema:

- **One basis, three ways in.** Stating `lawfulBasis` on `POST …/ropa` writes the activity and its DRAFT basis record in the same transaction, so the register cannot gain a line with an unstated justification half-written. The same happens on `linkRopaLawfulBasis` afterwards, and the audit row is the activity's (`ropa_activity.lawful_basis_linked`) because that is the screen the person was on.
- **An activity can hold more than one basis, so the read shape is a list.** The sample modal offers one select, and the API answers with what the domain actually is: `CONSENT` for a marketing list and `LEGAL_OBLIGATION` for the payroll record behind it are both true of one activity. A client that shows one choice is choosing which of the linked records to display, not describing the contract.
- **The counts are the server's, not a re-count in the browser.** `unlinked` cannot be derived from the page the client is holding, because the page is a cursor page of a register that may be longer — the same reason the review counts were already computed in `GET …/ropa/monitor`.
- **The PDF is a third synchronous template, and it is built from the catalogue entry.** `src/reports/definitions/ropa-register.ts` is the only place its id, version, title and description exist; `GET …/reports/catalogue` lists it, the RoPA screen's Export PDF calls `POST …/reports/ropa-register`, and the record stores the snapshot of the rows it printed. It prints at most 300 activities and says how many it left out.

## 0.11.0 - Phase 9a reports and the audit trail: catalogue, history, async generation, the Consolidated DPO Report, trail search and CSV export (additive)

New endpoints (under `/api/v1`; every operation carries `x-access` / `x-permission`). Nothing was removed or renamed: 148 paths become 153 (5 new operations, 14 new schemas), and two existing report schemas **widened**: `ReportDto.size` and `ReportDto.sha256` became nullable and `ReportParamsDto` gained `period` and `confidential`. A client that assumed every report record has bytes must now handle `null` — that is the point: a report can exist before its document does.

**The report routes need migration `20261019120000_phase9a_report_generation`** (`reports` gains `template_version`, `finished_at`, `error_code`, `error_detail`, `updated_at`; `data_snapshot`, `storage_key`, `sha256` and `size` become nullable until a render finishes, and the stored check keeps `READY` meaning "the bytes are there" and `FAILED` meaning "a code and a reason are"), which is not applied until the owner applies it — until then every report **generation** route answers `500 INTERNAL_ERROR`. The read routes (catalogue, history, audit) need no migration: they read what Phase 2a and the earlier phases already wrote.

New error codes: `EXPORT_RANGE_TOO_LARGE` (422 — narrower period, not a smaller row set) and `REPORT_GENERATION_FAILED`, which is a **stored** `errorCode` on a `FAILED` record rather than an HTTP status: the request that queued the document already succeeded. Reused: `CONFLICT` (409), `NOT_FOUND` (404), `FORBIDDEN` (403), `VALIDATION_FAILED` (400). Phase 9a adds **no permission key** — `audit.view`, `audit.export`, `reports.view` and `reports.export` were already in the catalogue, so [docs/rbac-matrix.md](../docs/rbac-matrix.md) gains no row.

Behaviour that is not visible in the schema:

- **The catalogue is data, not prose.** `src/reports/definitions/registry.ts` holds every template definition and is the only source for both `GET …/reports/catalogue` and the permission the decorators require (`REPORT_PERMISSIONS`), so what the API advertises and what it enforces are one constant. A template that exists in the code but not in the registry does not exist; planned ones are listed with their phase instead of being hidden.
- **Async where the document needs it, synchronous where one request can honestly carry it.** The two single-payload templates keep rendering in the request and answering `201` with a `READY` record — Phase 5 and Phase 8 behaviour is unchanged. The DPO pack writes its `PENDING` row and enqueues `report.generate` in the **same transaction** (`dedupeKey: report-generate:<reportId>`) and answers `202`; the runner renders, stores through the `StorageProvider` and writes `READY`.
- **A record cannot be written twice.** `markReady` and `markFailed` update only a row that is still `PENDING`; when that guard finds nothing, the bytes just uploaded are deleted again, so two runners cannot both settle one report and the loser leaves no orphan object. Only the **last** attempt records `FAILED`, with `error_code` and a `sanitiseError` detail — earlier attempts rethrow so the job's backoff applies, and no driver message reaches the record.
- **Nothing is invented about a period.** The window is computed in the organisation's timezone from `SettingsService` (`last_30_days` is today minus 29 days, `this_year` starts `01-01`), and the inclusion rule is printed in the document: a record counts when it was **open during** the window, not only when one date field falls inside it — the legacy DPO report hid stale-but-open records and ignored the window for retention.
- **The report reads the registers the way the screens do.** Six modules (`Ropa`, `Risks`, `LawfulBasis`, `Dsar`, `Breaches`, `Retention`) now export their service so `ConsolidatedDpoService` can page through the same list endpoints; no report-only query filter, no second count, no raw SQL. Reads are bounded (100 rows per page, a scan cap, at most 60 printed rows per section) and the document states how many rows it did not print, because a report that silently stops is worse than one that says it did.
- **An outward-facing document has a privacy shape.** The DSAR section prints no data-subject names or contact details — `reports.view` reaches a Compliance Manager while `users.view` does not — and the section says so in the document itself. Same rule on the trail: `actorUserId` is an id, never a name or an address.
- **A queued report stays queued until something ticks the runner.** `POST /api/v1/internal/jobs/tick` drains `report.generate` (and everything else), and no scheduler is configured in this build, so on a function host an async report is `PENDING` until the host's cron calls it. That is the honest state of the deployment, and the history list shows it as such.



## 0.10.0 - Deployment: the upload cap becomes the server's statement, files move to object storage (additive)

Nothing was removed, renamed or re-typed: one existing read gains one field and two multipart descriptions stop quoting a number the server no longer fixes. **No migration.** Phase 9a takes the next minor (0.11.0).

| Method | Path | operationId | Access | Notes |
|---|---|---|---|---|
| GET | `/api/v1/meta` | `getMeta` | public | gains `evidenceMaxBytes`: the largest evidence file this deployment accepts, in bytes. It is `EVIDENCE_MAX_BYTES` (default 4194304), so a client states the limit it read instead of carrying a number of its own into the message it shows an uploader |
| POST | `…/evidence`, `…/evidence/{id}/versions` | `uploadEvidence` · `uploadEvidenceVersion` | `governance.edit` | the `file` part and the `413` response no longer say "10 MiB": the multipart interceptor still bounds the body at 10 MiB, and the cap a request is refused against is the one `GET /api/v1/meta` states |

Behaviour that is not visible in the schema:

- **Where the bytes live is configuration, not code.** `STORAGE_DRIVER=s3` stores evidence, report PDFs and the logo in an S3-compatible bucket (Supabase Storage speaks the protocol, so do R2, B2, Wasabi and AWS S3) behind the same `StorageProvider` contract (ADR-0007). Keys, checksums and the authorised download endpoints are unchanged; the bucket is private and no object has a URL of its own. `validateEnv` refuses `s3` without an endpoint, bucket, region and both keys, and refuses `local` in production, because a host that can discard the instance's disk cannot keep a compliance file on it.
- **The same application answers from a function.** `src/main-serverless.ts` builds the Nest app once per warm instance and hands every request to the one Express instance `configureApp` set up, so the prefix, CORS, helmet, the problem+json filter, throttling and the request id are not a second implementation. `api/index.mjs` re-exports it and `vercel.json` routes everything to that one function.
- **A function host sets the ceiling twice over.** Vercel refuses a request body over 4.5 MB before any application code runs, which is why the default upload cap is 4 MiB and not the 10 MiB the pipeline can hold. `TRUST_PROXY=1` there: without it the per-IP limits and the lockout counters key on the proxy's address.
- **Queued jobs stay queued.** Outside development `JOBS_RUNNER` defaults to `external`, and a function is not running between requests: nothing is delivered or generated until something calls `POST /api/v1/internal/jobs/tick` with `JOBS_TICK_SECRET` set. No scheduler is configured in this build, which is the honest state of alerts and reports, not a defect of it.
- **Nothing is delivered by email yet.** `MAIL_TRANSPORT` still has one value (`file`), and a function's disk is not a mailbox. Production mail remains the provider decision it was.

New error code: `FEATURE_UNAVAILABLE` (503). It is deliberately not `SERVICE_UNAVAILABLE`: the server is healthy and retrying changes nothing, so a client must not queue the call again. Behaviour that is not visible in the schema:

- **Which assessment work is the organisation's finding.** An item counts only when its cycle is `IN_REVIEW` or `APPROVED` (a draft is somebody's work in progress; a superseded cycle is the older revision of work that has since been re-signed), and per subject only the newest revision counts. A subject is its `requirementId`, else its governance area with the business unit, else the item itself; newest is the latest sign-off instant (`approvedAt`, then `submittedAt`, then `createdAt`), with the cycle id last so the answer is stable rather than a coin toss. Everything is then rolled up by the same `summarise()` a per-assessment summary uses.
- **Two band sets do not make one average.** The counted set carries each cycle's methodology; one pair gives the exposure mean and its band, more than one pair answers `availability: unable_to_calculate` and names them in `methodologies`. Maturity and gap are levels, not exposure scores, and stay measurable.
- **The dashboard adds no second copy of a number.** The risk counts and the 5×5 grid, the RoPA monitor, the priority matrix, the DSAR SLA and the breach summary keep the endpoints that already compute them (`…/risks/summary`, `…/risks/heatmap`, `…/ropa/monitor`, `…/priority-matrix`, `…/dsar/sla`, `…/breaches/summary`) and the screen calls those; `docs/metrics/README.md` requires the dashboard's cards to be those counts, not recomputed ones. The Executive Dashboard PDF is drawn to the same rule and leaves the incident sections to the Consolidated DPO Report (Phase 9a).
- **An absent figure is explained, never invented.** Unmeasured is `null` with its coverage, never `0`; a framework or a register with nothing rated is `not_assessed`, never a percentage and never a verdict; `compliant` means "every assessed subject already reaches its own target" and is shown as "Meets target". Every payload repeats `asOf`, the highlight threshold and the `disclaimer` so a client has nothing to hard-code.
- **One unit of work per read.** Each dashboard call opens one transaction and a handful of set-based reads (`findMany` with a narrow `select`, one `groupBy`, one task read for the page) — never a query per card and none per row. Dates are calendar days in the organisation's zone.
- The Executive Dashboard report snapshots the four payloads exactly as the endpoints answered them, so a later screen that disagrees with a stored PDF can be compared against what was actually rendered. Generation and every download are audited (`report.generated`, `report.downloaded`); the audit row records the shape of the document, not its names.
- Phase 8 adds no permission key: `dashboard.view` and `ai.run` were already in the catalogue, so `docs/rbac-matrix.md` gains routes, not roles.

Behaviour that is not visible in the schema:

- **A deadline is frozen when the record is written.** `policyId`, the window in days and both dates come from the `deadline_policies` row in force at that moment; editing the policy afterwards changes nothing that already exists. Extensions are arithmetic on the record's own date (`new_due_on = previous_due_on + days`), never a recomputation from the policy.
- **The software ships no statutory number.** Every window is an organisation's own choice, recorded in the audit trail as `deadline_policy.updated`. A request or breach created with no policy in force simply has no due date: its deadline state is `not_configured`, it is never counted as late, and its alerts are never queued.
- **Dates are calendar days in the organisation's time zone.** "Overdue", "due soon" and the annual breach count are all decided against `todayIn(org.timezone, now)`, and an alert runs at 08:00 local on the day it names — computed with the zone's offset for that day, so a deadline is never announced as passed while it still has hours to run.
- **Alerts are one ledger row plus one outbox job, and they are idempotent.** The dedupe key is `<kind>:<recordId>:<deadlineDay>`, so a retried job lands on the same row; a second queue for an unchanged deadline writes nothing. A row is created `QUEUED` and only its outcome ever changes — the database refuses any other update and refuses DELETE, so "was anybody told" keeps its answer. Nothing here deletes an alert, and a skip stays visible with its reason (`NO_RECIPIENT`, `PREFERENCE_OFF`, `STALE_DEADLINE`, `ALREADY_HANDLED`).
- **Recipients (AC-BRC-02).** An incident alert goes to the organisation's designated data protection contact, or, when there is none, to the addresses of its active Company Owners in a stable order — a recipient who holds no account at all is still a valid recipient. A reminder's alert goes only to its assignee, and an unassigned reminder records `NO_RECIPIENT` instead of re-addressing the warning.
- **Alert emails are link-only.** The body names no requester, no breach, no count and no risk; the deep link is `<APP_BASE_URL><page>?open=<recordId>` with `<page>` one of `/dsar-tracker`, `/breach-registry`, `/reminders`, so the frontend pages of this phase have to honour an `open` query parameter. The subject line may name the organisation and the ROLE a message is addressed to, never a person.
- **Closure evidence, not closure text.** COMPLETED and REFUSED requests need an attached evidence row: the tracker records that the response was made and where the proof is, and keeps the response itself out of the register.
- Nothing in Phase 7 deletes. Requests complete, refuse or withdraw; breaches close; reminders finish or cancel; a superseded evidence version stays; the communication log, the chronology, the notification-decision ledger, the extension ledger and the alert ledger only grow.
- Register text is audited as `'changed'`, not by value, and a DSAR's subject details (name, email, notes) never enter the audit trail, a job payload, a log line or an email. Decisions — an extension reason, a status note, a notification decision, a cancel reason — are attributed and kept.
- `deadline_policies` deliberately has no `source`/`verified_by`/`verified_at` provenance columns (the domain reference mentions them): these windows are the organisation's own numbers with an audit trail, and there is no framework-derived window to cite. Recording provenance for numbers nobody published would be a claim, not a fact. This is a documented deviation, not a missing feature.
- Two reading choices that the metric and lifecycle rules force: a REFUSED or WITHDRAWN request falls in the SLA's `notMeasured` bucket (the percentage measures requests answered against their deadline), and containment is a chronology kind rather than a breach status.
- Phase 7 adds no permission key, so `docs/rbac-matrix.md` is unchanged: `data.view/create/edit`, `governance.view/create/edit/approve`, `reminders.view/manage`, `notifications.own`. Where the rule depends on the row (a status step, a review outcome, a reminder's owner) the handler declares `@OrganisationMember()` and the service decides, because a decorator can only name one permission.
- Every write is audited inside the same transaction as the change; an alert is queued inside the transaction that writes the record; no mail send or storage call happens while a transaction is open (a version upload writes the object first and rolls the row back by deleting it if the transaction fails). New audit actions: `deadline_policy.updated`; `dsar_request.created/updated/status_changed/identity_verified/extended/communication_added/evidence_linked/evidence_unlinked`; `breach.created/updated/status_changed/chronology_added/decision_recorded/evidence_linked/evidence_unlinked`; `evidence.version_uploaded/review_changed/scan_attested`; `reminder.created/updated/completed/cancelled/preference_updated`.

Behaviour that is not visible in the schema:

- The risk register's arithmetic lives in `src/domain/risk/policy.ts` and is the same arithmetic the database checks: score = likelihood × severity (both 1–5), and the band comes from the `risk_matrix_v1` reference bands (Low 1–5, Medium 6–11, High 12–19, Critical 20–25). A client sends factors and never a score or a level; a row whose four columns disagree cannot be written.
- Phase 6 uses those reference bands for every organisation. Making the risk bands configurable per organisation is a recorded deviation from the plan, not a missing feature.
- Residual risk may only reduce inherent risk: both residual factors must be present, the inherent pair must exist, and neither residual factor may exceed its inherent counterpart. Controls cannot inflate a risk.
- Acceptance is a decision in an append-only ledger, not a status a row is edited into. The ledger row is written before the status changes, because the status is a claim about the ledger and a database trigger enforces that the two agree (`status = 'ACCEPTED'` requires the newest ledger row to be an ACCEPTED decision). A withdrawal appends a WITHDRAWN row; nothing is ever edited away.
- `summary` and `heatmap` count the risks that are not CLOSED: a closed risk is history rather than exposure. `total` and `byStatus` still cover every row, and a risk with no complete factor pair is counted as `NOT_SCORED` / `unscored` instead of being placed on the grid or left out of the totals.
- All five registers share one review model (`src/domain/registers/review.ts`): `nextReviewDate` (or the risk's `reviewByDate`) is the only due date that counts, and it is always set by a person. `reviewIntervalDays` is cadence metadata and is never used to invent a deadline. No date is `not_reviewed` — that is a fact about the data, never "overdue" and never "on time" — and the lead window is the reference default of 30 days. Every state is decided against today in the organisation's own time zone.
- The registers use only permissions that already existed (`data.view/create/edit/delete`, `governance.view/create/edit/approve`); nothing was added to the catalogue, so `docs/rbac-matrix.md` is unchanged. Where a route's rule depends on the row (a status step, a review move) the handler declares `@OrganisationMember()` and the service decides, because the catalogue can only name one permission per decorator.
- Register text (a risk's description, a rule's data category, an activity's purpose) is audited as `'changed'` rather than by value: the trail records that a person edited the record, and does not copy the personal-data description of it into the audit log. Decisions — an acceptance rationale, a hold reason, a status reason — are attributed and kept.
- Nothing in Phase 6 deletes. Rules, levels, activities and basis records are archived, holds are released, and the disposal log and the acceptance ledger only grow. A legal hold row is immutable apart from its release columns, and a database trigger refuses its deletion outright.
- Every write is audited in the same transaction as the change, and every read and write runs inside the unit of work, so row-level security applies. New audit actions: `risk.created`, `risk.updated`, `risk.status_changed`, `risk_acceptance.accepted`, `risk_acceptance.withdrawn`, `classification_level.created/updated/archived/unarchived`, `ropa_activity.created/updated/archived/unarchived/evidence_linked/evidence_unlinked`, `lawful_basis_record.created/updated/archived/unarchived/review_status_changed/evidence_linked/evidence_unlinked`, `retention_rule.created/updated/archived/unarchived`, `legal_hold.placed`, `legal_hold.released`, `retention_disposal.recorded`.

| POST | `/auth/login` | `login` | 200 `{ accessToken, tokenType, expiresInSeconds }` | sets the HttpOnly `fca_refresh` cookie (path `/api/v1/auth`); `401 INVALID_CREDENTIALS`, `403 EMAIL_NOT_VERIFIED`, `429 RATE_LIMITED` + `Retry-After` |
| POST | `/auth/refresh` | `refreshSession` | 200 (same body) | cookie + header `X-Requested-With: fca-web`; rotates the cookie; `401` clears it |
| POST | `/auth/logout` | `logout` | 204 | cookie + `X-Requested-With: fca-web`; idempotent |
| POST | `/auth/forgot-password` | `forgotPassword` | 202 | uniform |
| POST | `/auth/reset-password` | `resetPassword` | 204 | body `{ token, password }`; ends every session |
| GET | `/me` | `getMe` | 200 `{ id, email, fullName, emailVerified, createdAt }` | needs `Authorization: Bearer` |

New error codes: `INVALID_CREDENTIALS`, `EMAIL_NOT_VERIFIED`, `INVALID_TOKEN`.

Behaviour changes that are not visible in the schema:

- Every route other than `/health*`, `/meta` and `/auth/*` now requires a bearer token (deny by default).
- Email links open SPA pages and carry the one-time token in the URL **fragment**: `/verify-email#token=...`, `/reset-password#token=...`; the SPA POSTs it. Other SPA paths used by emails: `/login`, `/forgot-password`.
- `POST /internal/jobs/tick` exists but is an operational endpoint (HMAC-signed), deliberately **not** in this contract.

## 0.1.0 - Phase 0 baseline

- `GET /health` liveness, `GET /health/ready` readiness (database), `GET /meta` build + contract version.
- Errors are RFC 9457 `application/problem+json` with stable `code`, optional `errors[]` and `requestId`.
