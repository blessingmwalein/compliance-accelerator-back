# Database and tenancy

## When to use
Any change to `prisma/schema.prisma`, `prisma/migrations`, a `*.repository.ts`, seed data, or anything that reads/writes tenant data. Always load together with `backend-architecture` and `security-and-rbac`.

## Rules

### Tenant model (MUST)
1. **Every tenant-owned table has a non-null `organisation_id`** (UUID FK to `organisations`). Reference/catalogue tables (frameworks, plans, permission catalogue) are *global* and listed in `GLOBAL_TABLES` with the reason (`src/database/catalogue.ts`, next to `TENANT_MODELS` and `TENANT_ROOT_TABLES`). A new tenant model must be added to `TENANT_MODELS` in the same change, or `npm test` fails.
2. **Composite foreign keys**: child rows reference their parent with `(organisation_id, parent_id)` so a row can never point at another tenant's parent. Add `@@unique([organisationId, id])` on parents to allow it. Never `ON DELETE SET NULL` on a tenant-scoping column.
3. **Defence in depth, in this order**: (a) the global `AccessGuard` resolves membership and enriches `RequestContext` (AsyncLocalStorage, `src/tenancy`); (b) every repository extends `TenantRepository` (`src/database`) and reads `this.organisationId` from the scope, so its methods **cannot be called without** a tenant and no id is ever a parameter, no bare-id lookups: `findById(id)` always filters `{ id, organisationId }`; (c) the Prisma safety net (`assertTenantScoped`, wired in `PrismaService.db`) **asserts** (it does not inject) that `organisationId` is pinned to the request tenant in `where` (reads, updates, deletes; top level, compound unique, or inside `AND`) or `data` (creates, upserts) and throws `TenantScopeError` otherwise, including on unknown operations and outside a tenant scope; (d) composite FKs; (e) **Postgres RLS** as the backstop (**ON since Phase 2c**, ADR-0004): `ENABLE` + `FORCE ROW LEVEL SECURITY`, policy `organisation_id = current_setting('app.org_id', true)::uuid`, set per request with `set_config('app.org_id', $1, true)` **inside the request transaction**; runtime connects as a non-owner role without `BYPASSRLS`; migrations run as the owner; fail closed when the setting is missing. **Consequences you must respect:** read and write tenant data only inside `uow.run` (a bare tenant query sees no rows, silently, it does not error); tenant repository methods take `tx`; a migration that adds a tenant table ends with `SELECT fca_enable_tenant_rls('<table>')` (`rls.int-spec.ts` fails for a tenant table without a policy); reads that happen before a tenant is known (membership check, the caller's organisations, invitation by token, platform list) go through the SECURITY DEFINER functions (`fca_membership_of`, `fca_memberships_of_user`, `fca_invitation_by_token`, `fca_platform_organisations`: fixed `search_path`, server-verified arguments only, `EXECUTE` granted in `runtime-role.sql`), never through an ad hoc bypass; a new organisation's id is generated up front (`uuidv7()`) so the very first insert can satisfy its own policy.
4. A record that exists but belongs to another tenant is reported as **404**, never 403.
5. The catalogue test (`test/database/catalogue.spec.ts`, runs in `npm test`, parses `prisma/schema.prisma` through `test/support/schema-catalogue.ts`) fails the build when a table has neither `organisation_id` nor a catalogue entry, a table lacks `@@map`, an id is not `uuid(7)`, `organisationId` is nullable or unmapped, a tenant table has no index starting with `organisationId`, or a tenant-to-tenant relation is not a composite FK with a matching `@@unique` target. Each rule is proven to fail on a planted violation. "If RLS is on, every tenant table has a forced policy" is an integration check to add when RLS is adopted.
6. **Await Prisma queries inside the request scope.** Queries are lazy thenables: the safety net runs when they are first awaited. `RequestContext.run` starts a returned thenable inside the scope, but a query handed un-awaited to code outside the scope fails with `TENANT_CONTEXT_MISSING`. Repositories use `this.prisma.db` (the checked client) or the `tx` from `UnitOfWork.run`; the plain client is private to `PrismaService`.

### Schema conventions
- Table/column names `snake_case` plural tables via `@@map`/`@map`; Prisma models `PascalCase`. UUID primary keys `@id @default(uuid(7)) @db.Uuid` (UUIDv7, generated by Prisma client-side: Prisma 7.10 supports it, so raw-SQL inserts must supply an id; the catalogue test enforces it). All instants `timestamptz` (`@db.Timestamptz`); date-only business dates (`due_on`, `review_on`) are `@db.Date`.
- Standard columns: `id`, `organisation_id`, `created_at`, `updated_at`, `created_by`, `updated_by` (nullable user FK), `version` (int, optimistic concurrency), `deleted_at` (only where soft delete is justified: records with legal/audit value; hard-delete elsewhere).
- Enums for closed sets that the contract exposes (statuses, severities); lookup tables for sets users may extend (classification levels).
- Raw inputs are stored, derived values are not: store sensitivity/severity/likelihood and `methodology_version`, compute exposure/level/gap in `domain/`; where a snapshot is required (approved assessments, reports) store the computed result **with** the methodology version and band snapshot.
- Unassessed means `NULL`, never a default score. No `DEFAULT 2`-style invented maturity.
- Indexes: every tenant table has an index starting with `organisation_id`; add `(organisation_id, status, due_on)`-style composites for the dashboard and reminder queries; uniqueness is always per organisation (`@@unique([organisationId, code])`).

### Migrations (MUST)
- Created with `npm run db:migrate:dev -- --create-only` against the **dev** Neon branch only; applied elsewhere with `db:migrate:deploy`. **Never edit an applied migration**; fix forward. Hand-written SQL that Prisma cannot model (CHECK constraints, triggers) is appended to the generated migration under a "Hand-written additions" banner **before** the first apply; the first migration has not been applied anywhere yet, so it still follows this rule. Append-only tables get a trigger (`RAISE EXCEPTION` with the default error code: Prisma hides the message of a class 23 SQLSTATE) **and** a REVOKE in `prisma/sql/runtime-role.sql`.
- Offline generation (`prisma migrate diff --from-empty --to-schema ... --script`) prints nothing without a syntactically valid `DIRECT_URL`; review the SQL and check it on any PostgreSQL before it reaches Neon.
- Expand/contract: add nullable → backfill → enforce; drop in a later release. Destructive steps need an explicit note in the migration SQL comment and the phase report.
- Migrations and the Prisma CLI use **`DIRECT_URL`** (non-pooled). The running app uses **`DATABASE_URL`** (pooled) through `@prisma/adapter-pg`. Mixing them up causes "prepared statement already exists"-style and lock errors.
- `prisma generate` must work with no environment (it does: `prisma.config.ts` only sets `datasource.url` when `DIRECT_URL` exists); `postinstall` runs it.

### Neon specifics
- Branches: `main` = production (reserved), `dev` = local development, `test` = integration tests (destructive!). Each has its own pooled (`…-pooler…`) and direct connection string; `sslmode=require`.
- Pooler = PgBouncer in transaction mode: **no session state** between statements: no `SET` outside a transaction (use `set_config(..., true)` inside one), no session advisory locks (use `pg_advisory_xact_lock`), no `LISTEN/NOTIFY`, no long idle transactions. Interactive transactions must be short.
- **Cold starts**: compute scales to zero; the first query after idle can take seconds. Keep `DATABASE_CONNECT_TIMEOUT_MS` generous (default 10 s), make readiness probes tolerant, and retry the first connection in test setup.
- The destructive-test guard (`test/support/test-database.ts`) refuses to run integration tests unless the database name in `TEST_DATABASE_URL` and `TEST_DIRECT_URL` contains `test`, both name the same database and endpoint, neither equals `DATABASE_URL`/`DIRECT_URL`, and `ALLOW_DESTRUCTIVE_TESTS=true`. Neon's default database is `neondb` on every branch, so create a `fca_test` database on the `test` branch.
- **The session TimeZone must be UTC.** Prisma's pg adapter writes timestamps without an offset, so a non-UTC session silently shifts every stored instant and every `now()` comparison (found when an embedded database inherited a UTC+2 machine). Neon defaults to UTC; `runtime-role.sql` pins `ALTER ROLE fca_app SET timezone = 'UTC'` (role-level settings survive the pooler); `test/database/session-timezone.int-spec.ts` checks it.
- The runtime connects as the non-owner `fca_app` role (`prisma/sql/runtime-role.sql`, re-run after every migration that adds tables); migrations and test resets use the owner on the direct URL.
- Region choice is a **data-residency decision** (CDPA/POPIA cross-border transfer rules): record it in ADR-0004/`docs/neon-setup.md` before production data is loaded.

### Seeds and reference data
- Reference data (frameworks, requirements, mapping packs, permission catalogue, plans) is loaded by versioned, idempotent seed scripts with provenance (`compliance-frameworks`). Seeds never overwrite user-maintained rows.

### Global reference data that must not change (Phase 4)
`framework_versions`, `requirements` and `mapping_pack_entries` are global (in `GLOBAL_TABLES` with the reason), written ONLY by the owner-run loader. Enforce it twice: `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ... FROM fca_app` in `prisma/sql/runtime-role.sql`, and BEFORE UPDATE/DELETE triggers that freeze anything beyond a draft (the owner role is bound too). Tenant tables may point at them by plain foreign keys. Reads from global tables go through `PrismaService.db` or the unit-of-work client, never need `app.org_id`.

## Example

```prisma
model BusinessUnit {
  id             String   @id @default(uuid())
  organisationId String   @map("organisation_id")
  code           String
  name           String
  version        Int      @default(1)
  createdAt      DateTime @default(now()) @map("created_at") @db.Timestamptz
  updatedAt      DateTime @updatedAt @map("updated_at") @db.Timestamptz

  organisation Organisation @relation(fields: [organisationId], references: [id], onDelete: Restrict)
  ropas        ProcessingActivity[]

  @@unique([organisationId, id])        // target of composite FKs from children
  @@unique([organisationId, code])      // codes are unique per organisation, not globally
  @@index([organisationId, name])
  @@map("business_units")
}

model ProcessingActivity {
  id             String @id @default(uuid())
  organisationId String @map("organisation_id")
  businessUnitId String @map("business_unit_id")
  // composite FK: the unit must belong to the SAME organisation
  businessUnit BusinessUnit @relation(fields: [organisationId, businessUnitId], references: [organisationId, id])
  @@map("processing_activities")
}
```

```ts
// repository: the tenant is implicit, never a parameter the caller can forge
async findById(id: string): Promise<BusinessUnitRecord | null> {
  return this.prisma.db.businessUnit.findFirst({ where: { id, organisationId: this.organisationId } });
}
```

## Anti-patterns
- `findUnique({ where: { id } })` / `update({ where: { id } })` / `delete({ where: { id } })` without the organisation.
- A tenant id taken from the request body or query string; `Company.list()[0]`-style "the first company wins".
- Persisting derived scores; defaulting unassessed values; storing a framework as a hard-coded string list.
- Running migrations through the pooled URL; `SET search_path`/`SET app.org_id` outside a transaction; session advisory locks.
- Running integration tests against `dev` or `main`; sharing a test database between parallel workers.
- Editing an applied migration; dropping a column in the same release that stops using it.

## Checklist
- [ ] New table has `organisation_id`, composite FKs to tenant parents, per-organisation unique keys, an `organisation_id`-leading index
- [ ] Repository extends the tenant base; no bare-id access; list queries bounded
- [ ] Nullable = unassessed; no invented defaults; derived values computed, snapshots carry methodology version
- [ ] Migration generated on `dev`, reviewed, expand/contract respected, applied with `deploy` elsewhere
- [ ] Catalogue/tenancy tests updated (`GLOBAL_TABLES`, fixtures, matrix)
- [ ] Neon rules respected (pooled runtime, direct migrations, no session state)
